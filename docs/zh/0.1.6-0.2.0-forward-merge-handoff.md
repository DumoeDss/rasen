## 3. 合并策略结论

### ❌ 不要走 `0.1.6 → main → 0.2.0`

三个独立硬伤：

1. **main 是发版干线，不是运输管道。** 本仓发版模式是 `609a547f Merge dev/0.1.5 — release 0.1.5` 那种——**发版时**才把 dev 分支合进 main 再打 tag。在 0.1.6 未发版时合进 main 等于把未发布工作灌上发版干线。
2. **`main → 0.2.0` 本身是三方合并，会污染 0.2.0。** main 不是 0.2.0 的祖先（领先 9 commit），会把 release 合并提交、版本戳、空白清理一起拖进 0.2.0 的 dev 线。
3. **绕路不省事，反而多一层冲突。** 两线的并行分歧（edit-boundary 双重退休、CLI 结构差异）无论走哪条路都得人工 reconcile 一次；绕 main 只额外引入 main 那 2 个无关提交。

### ✅ 正确做法：dev 分支之间直接正向合并，main 只在发版时被碰

```
dev/0.1.6 ──forward-merge──▶ dev/0.2.0     （dev 线之间的下合并，方向:老线→新线）
dev/0.1.6 ──release merge──▶ main ＋tag     （0.1.6 发版时）
dev/0.2.0 ──release merge���─▶ main ＋tag     （0.2.0 发版时）
```

**为什么正向合并反而让两次发版各自合 main 更干净**（这正是常见顾虑）：

- 先做 `dev/0.1.6 → dev/0.2.0`，则 `dev/0.1.6` 成为 `dev/0.2.0` 的祖先。
- 0.1.6 发版：`dev/0.1.6 → main`，main 拿到 0.1.6 工作。
- 0.2.0 发版：`dev/0.2.0 → main`。此时 `dev/0.1.6 ⊆ dev/0.2.0`，而 main 已含 `dev/0.1.6`，git 自动把已共同的提交当祖先，**只把 0.2.0 独有的工作合进去，不会重复应用 0.1.6 的工作**。

即：**正向合并不是制造"main 收两次 0.1.6"的问题，而是预防它。** 不做正向合并、各自发版合 main，反而会让 main 上出现两套 edit-boundary 退休实现打架。

**方向不可反：** 只能把较小/较老的 `dev/0.1.6` 合进 102 commit 的 `dev/0.2.0`；反向会把未发布的 0.2.0 工作倒灌进 0.1.6 发版线。

## 4. file-placement 文件夹结构（索引，非重复）

权威设计见 [`file-placement-and-planning-roots.md`](./file-placement-and-planning-roots.md)（2026-08-01 更新，由 PR #121 closure 协调至与实现一致）。核心要点：

- **一条不变量：** agent 用文件工具读写的路径必须在 planning root 或 execution root 内；machine root（`~/.rasen/`）只存 CLI-owned 状态，agent 永不直接引用。
- **三种 root：** planning（规划事实源，含 Archive）、execution（代码 checkout/worktree）、machine（`~/.rasen/`，仅 CLI-owned）。
- **"内置/外置"不是用户配置项：** 每种文件类型落点由其所有者唯一确定，无 `internal|external` 开关。
- **七类文件 → 所有者 root：** 固定规划文件/design-docs/evidence/handoff → planning；probes/ephemera → execution；coordination → machine。
- **Archive 四档处置：** 归档 / 清理 / 静置 /（design-docs 与 coordination 在作用域之外）。
- **`archive.json` 不记录 planning root 提交哈希**（闭不上的自我引用），只记 `codeCommit` + evidence 内容哈希。

详细路径树（in-project / Store / machine 三种形态）、分类判定顺序、迁移规则均见该文档。

## 5. 正向合并 dry-run 预演（2026-08-01 快照）

工具：`git merge-tree --write-tree`（内存三方合并，**不碰 HEAD/index/工作树/任何分支**）。两个场景：

| 场景 | ours（目标） | theirs（被合） | 冲突文件 | 合并总改动 |
|---|---|---|---|---|
| **A 基线**（不含 file-placement） | `dev/0.2.0` | `dev/0.1.6` | **13** | 72 |
| **B 真实目标**（含 file-placement） | `dev/0.2.0` | `fix/pr121` | **25** | 325 |

**重跑命令**（合并前必做，数字会漂）：

```bash
cd <repo>
# 场景 B: 把 PR121(含 file-placement) 合入 dev/0.2.0 的 dry-run
git merge-tree --write-tree --name-only --no-messages origin/dev/0.2.0 fix/pr121-file-placement-hardening
# 拆分 add/modify/delete 足迹(用上一步第一行的 resulting tree):
#   git diff-tree -r --diff-filter=A --name-only origin/dev/0.2.0 <tree>   # 纯新增
```

**325 这个数字极具欺骗性——拆开看：**

```
325 改动 = 187 纯新增（0.2.0 没有,直接落地,零冲突）
        + 138 已存在文件被合并
        + 0   删除
只有 25 个冲突,其余 300 个干净落地
```

### dry-run 的边界（重要）

`git merge-tree` 是**纯文本三方合并**：

- ✅ 能抓：行级冲突、新增/删除/修改文件清单与数量
- ❌ 抓不到：语义冲突（两段都干净合上但行为矛盾）、构建是否通过、测试是否绿、`rasen validate` 是否过、locale key 是否语义对齐

**dry-run 抓不到的已知隐患：**

- **edit-boundary 双重退休** 在 textual dry-run 里基本没炸（25 个��突里只有 `test/core/edit-boundary-vocabulary.test.ts` 一个相关），但两条线都各自有 `rasen/changes/archive/…-retire-runtime-edit-boundary/` 目录（0.2.0 是 2026-07-31、0.1.6 是 #119）。textual 合并可能把它们当内容相同的纯新增放过——**合并后必须人工核对这两个 archive 目录没重复/没分叉**。

真正合并做完后还必须跑：`tsc` + 测试套件 + `rasen validate` + 逐个核对第 ④ 类 spec/模板。

## 8. 推荐执行顺序

1. **把 PR #121 并入 `dev/0.1.6`**（MERGEABLE、CI 全绿、审查 CLEAN）。若 0.1.6 已前进则先 rebase PR121 到当前 tip。
2. **正向合并 `dev/0.1.6 → dev/0.2.0`**（方向不可反）。一次三方合并带过来 file-placement portfolio + CLI 文案拆分 #110 + codex bridge + 0.1.5 共有工作。**建议在临时 worktree 里做**,不污染主 checkout。
3. **人工 reconcile**（按第 5 节四类冲突的策略）:
   - 机械型(locale/completions/CHANGELOG):逐类取并集或取 theirs
   - 语义型(`archive.ts`/`work.ts`):对照 file-placement 设计文档裁决
   - port-delta 型(`runs.ts`/`pipeline-registry`):取 ours,手工回移 theirs 小改
4. **合并后验证**:`tsc` + 测试套件 + `rasen validate` + 核对 edit-boundary 双 archive 目录 + locale 树完整性。
5. **main 全程不动**,直到各自发版:`dev/0.1.6 → main` ＋ tag `rasen-v0.1.6`;`dev/0.2.0 → main` ＋ tag `rasen-v0.2.0`。
