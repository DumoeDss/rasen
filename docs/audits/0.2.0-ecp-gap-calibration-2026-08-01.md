# 0.2.0 ECP 缺口校准（2026-08-01）

> 状态：Direction calibration，**不是最终 completion audit**
> 分支：`dev/0.2.0`
> Git revision：`14ed62bc088197294f4a219ff20e946a6a99691d`

## 1. 版本边界

- 0.2.0：完整 Change-level Executable Composite Pipelines；
- 0.3.0：Issue、Execution Plan、Dispatch、`auto-decompose` 上移、跨项目编排；
- 0.3.0 不承接任何使 ECP 成立所必需的能力。

研究稿与历史 Result 中的 `0.1.6`/`0.1.7` 标签保留为当时的设计和证据；当前
版本真相由 ECP Target State、Roadmap 与本校准记录给出。

## 2. 已观察到的能力

- Definition v2、v1→v2 normalization、静态校验、immutable plan 与 digest 已存在；
- canonical Run Record、deterministic reconciler、engine ownership、恢复与
  projector 已落地；
- CompositeRef、BoundedLoop、ReviewCycle、GoalLoop、Choice、FanOut/Join 的
  runtime/Operations 主路径已实现；
- 默认 `runs.engine: auto` 对 `bug-fix`、`small-feature`、`full-feature` 和三个
  goal-loop built-in 选择 reconciler；
- `auto-decompose` 报 `execution_profile_unavailable` 并 fail closed，符合 0.3.0
  Issue/Dispatch 边界；
- fresh build 后，ECP-5 closure dogfood scenario D 通过真实 CLI 完成
  propose → apply → verify/review → triage → fix → re-review → ship → archive，
  最终 Run 为 `completed`、review outcome 为 `clean`；
- 既有 fault、ack-loss、archive/recreate、cross-plane、review、parallel 与 UI
  parity 测试覆盖面较强。

这些证据说明组合执行内核已经成形，但不能推出完整 ECP 已通过。

## 3. 0.2.0 发布阻塞缺口

### G1：v2 还不是默认公开创作真相

- `PIPELINE_DEFINITION_VERSION` 仍为 1；
- `pipeline init` scaffold 写出 v1；
- 空白 Canvas 从 `{ version: 1, stages: [] }` 开始；
- package built-in 源全部 authored v1；
- 每个 v1 preparation 都产生 `LEGACY_NORMALIZED` warning，且文案仍称
  “prompt-owned execution remain unchanged”，与 6 个 built-in 已由 reconciler
  执行的事实冲突。

兼容输入继续存在是正确设计；让新建入口继续默认 v1 不是兼容要求。

### G2：Canvas 与公开原语不对称

- v2 root palette 可创建 AtomicStage、Gate、Choice、Finish、CompositeRef、
  BoundedLoop；
- declaration body 可添加 AtomicStage 和 capability；
- FanOut/Join 面板仍是只读；
- GoalLoop 没有 v2 专用创作面，v1 goal loop 只能查看/保留；
- BoundedLoop 主要只可调整 max rounds，body phases、完整 exits、预算、stall/
  blocked/human policy 没有完整创作闭环。

因此“runtime 能执行该原语”不等于“Definition/Canvas/Runtime/Operations 四面
已经对称”。

### G3：通用 loop lifecycle 低于研究契约

公开 BoundedLoop 目前主要表达：

- `maxIterations`、可选 `maxActions`/`budget`；
- body outcome 到 `continue | exit` 的 mapping。

研究要求还包括 progress/stall、blocked、strategy exhaustion、human escalation
与完整 typed terminal outcomes。GoalCycle 有局部 stall 数据，ReviewCycle 主要
只有 `clean | exhausted`，尚未证明二者共享完整公共 lifecycle。

### G4：没有独立 Session executor

内核通过 `deliveryMode: grant | defer` 授予或封印 agent action；实际启动 agent、
session reuse、worker lifecycle、cancel/恢复与 usage 记录仍由 launcher 会话承担。
`docs/session-execution-layer-design.md` 明确记录当前没有 executor 实现。

这不否定 deterministic kernel，但阻止“无需 launcher 隐藏编排即可自宿主真实
Change”的产品闭环。

### G5：自宿主与最终发布证据缺失

- ECP portfolio 自身由旧 orchestration 路径交付；
- closure dogfood 的 action result 由 harness 驱动，不是独立 agent session
  实际完成一个后续工程 Change；
- 尚未在当前 HEAD 上重跑完整 completion audit 并关闭全部高优先级 finding；
- package 版本已在工作树中改为 0.2.0，但尚未形成 committed version、changelog、
  package、tag 与 release contract 的一致事实；
- legacy engine 的保留/默认关闭/退休尚未按真实发布周期证据决策。

## 4. 验证限制

- `pnpm build` 在当前工作树成功；fresh build 是必要条件，旧 `dist/` 会给出错误的
  support 结果；
- focused Vitest 未能启动，因为当前 `node_modules` 不完整：`vitest` shim 缺失，
  直接入口又缺少 `vite-node` 的 `debug` 依赖；
- 因此本记录不宣称当前 HEAD 的全量测试通过。最终审查前需先执行干净的 frozen
  dependency install，再串行运行 build、root/UI tests、typecheck、lint 和 pack/
  release checks，避免多个 build 同时删除 `dist/`。

## 5. 路线结论

当前不应删除历史 research、旧 audit 或 Slice result；应把它们标为历史证据，
并让当前文档只保留一个执行顺序：

```text
ECP-6 v2 Authoring and Loop Contract Closure
  -> ECP-7 Session Execution and Self-hosting
    -> ECP-8 Completion Audit and Release Truth
      -> 0.3.0 Issue / Dispatch
```

ECP-6 被列为唯一 NOW 候选，但必须通过 Direction Select 后才能成为 active Slice。
