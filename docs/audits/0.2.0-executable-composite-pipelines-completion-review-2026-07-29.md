## 1. 结论

**没有。当前并非所有 Pipeline 都已转为 Executable Composite Pipeline。**

当前实际交付可准确概括为：

> **Pipeline Definition v2 与 Canvas root-graph 基础已经建立；确定性的 root-DAG
> Change Run spine 已经落地，并用 `bug-fix` simple path 证明；但 Composite、
> BoundedLoop、ReviewCycle、GoalLoop、FanOut/Join 的执行仍未实现，Custom
> Composite 尚不能在 Canvas 中完整创作或通过 Reconciler 运行，`auto`、`goal`、
> `review-cycle` 也仍由 LEAD prompt/playbook 拥有机械推进。**

因此：

- 若以 `ecp-run-spine` 的局部目标衡量，核心实现已经相当完整，且 focused tests
  通过；
- 若以研究文档和 umbrella planning context 锁定的 **0.2.0 ECP 产品退出条件**
  衡量，当前状态是 **未完成、不可按该定义发布**；
- `docs/architecture/executable-composite-pipelines.md` 基本准确描述了已经落地的
  root-DAG slice，但它把这个 slice 重定义成“0.2.0 范围”并称为“权威架构参考”，
  与 tracked research 和 umbrella planning 的产品边界直接冲突。

不建议给当前状态一个伪精确的总百分比。更可信的进度事实是：

- 7 个串行子 Change 中，`ecp-definition-v2` 完成；
- `ecp-run-spine` 与两个补丁 Change 的代码已合入，但正式验证/收口 ledger 仍有
  未完成项；
- `ecp-review-cycle`、`ecp-custom-composite`、`ecp-goal-loop`、
  `ecp-full-feature`、`ecp-product-closure` 目前只有空 Change shell；
- 7 个内置 Pipeline 中，只有 `bug-fix` 的特定 simple root-DAG 形状存在
  Reconciler 路径；其余 6 个被 support analyzer 判为不支持；
- 在当前无 launch-time execution profile 的实际 CLI 视图中，7/7 都只列出
  `legacy` engine。

## 2. 两份文档的口径对照

### 2.1 研究文档锁定的是完整 ECP 产品闭环

`deterministic-pipeline-kernel-research.md` 对 0.2.0 的约束是明确且重复出现的：

- Definition v2、Canvas、Custom Composite、Compiler/Reconciler、canonical Run
  Record、Operations 是不可拆闭环；
- `bug-fix`、`small-feature`、三个 goal pipelines、`full-feature` 和至少一个
  Canvas-authored Custom Composite 都要完成真实 Run；
- ReviewCycle 与 GoalLoop 必须作为两个真实 BoundedLoop 消费者；
- `rasen-auto`、`rasen-goal`、`rasen-review-cycle` 必须收缩为薄入口；
- 0.3.0 不承接任何“使 ECP 成立所必需”的能力。

umbrella planning context 和 decomposition plan 继承了同一边界，并把实施拆为：

```text
ecp-definition-v2
  -> ecp-run-spine
    -> ecp-review-cycle
      -> ecp-custom-composite
        -> ecp-goal-loop
          -> ecp-full-feature
            -> ecp-product-closure
```

### 2.2 架构文档描述的是 root-DAG run-spine slice

`docs/architecture/executable-composite-pipelines.md` 明确写道：

- 0.2.0 范围是 root-DAG 内核、CLI/API/Operations UI 和 `bug-fix` simple path；
- Composite、BoundedLoop、GoalLoop、FanOut/Join 执行“不在范围内”；
- runtime 只接受 v1 root-DAG；
- complex adaptive verify 挂起，而不是进入 ReviewCycle。

这些描述与当前代码基本一致，但它们只对应 decomposition plan 的第二个 child
`ecp-run-spine`，不对应 umbrella 0.2.0 ECP 产品边界。

### 2.3 正确的文档层级

当前两份文档不能同时作为“0.2.0 权威范围”：

```text
研究文档 / umbrella planning
  = 0.2.0 产品目标与退出条件

现有架构文档
  = 已落地的 root-DAG run-spine slice 架构
```

除非项目明确接受一次范围变更，否则不能用后者静默覆盖前者。

## 3. 实际实现盘点

### 3.1 Pipeline 静态状态

对 `pipelines/*/pipeline.yaml` 全部执行了：

```text
node bin/rasen.js pipeline validate <path> --json
```

7/7 均通过，diagnostics 为空。这证明 YAML、stage id、DAG 依赖和当前 v1 contract
结构合法；**它不证明 Pipeline 可由 Reconciler 执行**。

当前 `pipeline show --json` 的实际支持矩阵：

| Pipeline | Authored format | 当前可用 engine | Reconciler 判定 | 主要原因 |
|---|---:|---|---|---|
| `auto-decompose` | v1 | legacy | 不支持 | decompose + review loop |
| `bug-fix` | v1 | legacy（show 时） | 仅特定启动 profile 下支持 | exact simple root-DAG shape |
| `full-feature` | v1 | legacy | 不支持 | parallel/condition + review loop |
| `goal-loop-evaluate` | v1 | legacy | 不支持 | goal loop |
| `goal-loop-measure` | v1 | legacy | 不支持 | goal loop |
| `goal-loop-research` | v1 | legacy | 不支持 | goal loop |
| `small-feature` | v1 | legacy | 不支持 | review loop |

这里的 authored v1 本身不是缺陷：研究明确要求 v1 可被兼容归一化。决定“是否已
迁移”的证据是 runtime support，而不是 YAML 顶部的版本号。

### 3.2 Definition / Compiler plane

已完成或基本完成：

- Definition v2 envelope；
- `AtomicStage`、`CompositeRef`、`BoundedLoop`、`Choice`、`FanOut`、`Join`、
  `Gate`、`Finish` 的公开类型与静态校验；
- v1 -> normalized v2；
- Composite recursion、nested loop、缺失 exit、port/capability/budget 等校验；
- immutable `ChangeRunPlan` envelope 与 digest；
- built-in/custom declaration 走同一静态 semantic model。

但 Definition 模块本身明确报告：

```text
authored v2:
  executable: false
  executionMode: unavailable
  unavailableReason: ecp_v2_runtime_unavailable
```

即：**Definition v2 已可表达、校验、round-trip，但尚不是可执行 v2。**

### 3.3 Canvas / authoring plane

已完成：

- v2 root graph 的读取、渲染、保存与校验基础；
- `AtomicStage`、`Gate`、`Choice`、`Finish` 的编辑；
- 全部八种 v2 node kind 的只读渲染和 typed handles；
- 不支持字段的无损保留；
- engine support panel 与服务端 support analyzer 对齐。

未完成：

- `CompositeRef`、`BoundedLoop`、`FanOut`、`Join` 编辑；
- Composite declaration/body 创建与编辑；
- Composite fold/expand；
- limits/exits/outcome ports 的完整 authoring；
- Canvas-authored Custom Composite 的真实 Run。

代码和测试将 `CompositeRef`、`BoundedLoop`、`FanOut`、`Join` 明确列为
“known later-slice kinds”，在当前 editor slice 中只读且不可删除。因此，研究文档
所要求的 Custom Composite Canvas 不是“基本完成”，而是尚未进入对应 child Change。

### 3.4 Runtime / Reconciler plane

已完成且有较强测试证据：

- canonical immutable Run Record；
- deterministic root-DAG reconciliation；
- AtomicStage、Gate、implicit/explicit Finish；
- action/result/control/completion/actor/evidence 的闭合 wire contract；
- crash-safe append-only store、idempotency、workspace reservation；
- engine ownership、archive/recreate identity、安全路径与 drift；
- CLI `start/status/resume/complete/control/cancel`；
- management runs API、Operations root-DAG view/control；
- `bug-fix` simple route 的 fresh-process E2E。

明确未完成：

- authored v2 lower；
- `CompositeRef` runtime；
- `BoundedLoop` / ReviewCycle / GoalLoop runtime；
- FanOut/Join barrier runtime；
- hierarchical composite/round/phase Run Record；
- open-finding/goal-progress 的领域 reducer；
- Composite crash/recovery；
- Custom Composite execution。

代码边界非常明确：

- lowerer “only supports the v1 bug-fix root-DAG shape”；
- `RuntimePlanNode` 只有 `atomic | finish`；
- reconciler 注释明确“不解释 Composite/BoundedLoop/GoalLoop/FanOut/Join”；
- support analyzer 只接受 exact `bug-fix` shape；
- complex adaptive verify 会产生持久 `capability-unavailable` wait。

因此当前成果应称为 **deterministic root-DAG Change Run spine**，而不是已完成的
Executable **Composite** Pipeline runtime。

### 3.5 Operations plane

已完成的是 root-DAG Operations：

- Run list/detail；
- frontier、action、wait、drift、terminal；
- resume/decision/escalate/cancel；
- CLI/API/UI 共享 `ChangeRunView/1` projector；
- other-worktree 只读与 record-version 冲突保护。

尚无研究要求的 Composite Operations：

- composite path；
- round/phase；
- open findings；
- goal score/evaluation/gaps；
- loop cap/stall/blocked/strategy；
- parallel member/barrier/budget；
- composite evidence 与 outcome mapping。

### 3.6 Launcher / compatibility plane

`rasen-auto`、`rasen-goal`、`rasen-review-cycle` 仍包含完整的 LEAD orchestration
playbook。尤其 `rasen-review-cycle` 仍明确写着：

- LEAD drives role-isolated subagents；
- LEAD 维护 review -> triage -> fix -> re-review loop；
- LEAD 维护 round、stall、blocked、strategy 和 `auto-run.json`；
- Pipeline runtime 只把 loop 当成一个 prompt-owned stage。

所以“三个入口已收敛为薄 launcher/preset/adapter”的退出条件尚未发生。

4. 以 support analyzer + real Run matrix 作为“所有 Pipeline 已迁移”的发布门；
5. 最后再提交版本、changelog、tag 和完整用户迁移文档。

### 若决定缩小 0.2.0

必须把这视为产品方向变更，而不是文档润色：

1. 新建正式 scope-change proposal；
2. 修改 research、umbrella planning、decomposition、roadmap 和 release contract；
3. 明确剩余 Composite/Goal/parallel/launcher work 进入哪个版本；
4. 重新命名当前交付，避免一个不执行 Composite 的版本被称作“Executable
   Composite Pipelines complete”。

## 9. Verdict

**CHANGES REQUIRED**

root-DAG Change Run spine 已经形成真实、可测试的执行内核，但 0.2.0 在权威研究
定义下仍缺失大部分使 “Executable Composite Pipeline” 成立的能力。当前最严重的
问题不是底座代码质量，而是产品范围、架构命名、Change ledger 和 release 状态彼此
不一致；在这些差异被正式解决前，不能宣称所有 Pipeline 已迁移，也不能宣称 0.2.0
ECP 产品闭环完成。
