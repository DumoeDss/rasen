## Requirements
### Requirement: Issue creation assigns identity before publishing content

The Store Issue creation operation SHALL require a non-empty title and SHALL assign an immutable
Issue UID and immutable human Issue key before publishing the Issue record. The UID and key SHALL
be generated by the system and SHALL NOT be derived from operator-authored identity input. Repeated
titles SHALL be permitted and SHALL receive distinct identities. Allocation failure SHALL publish
no Issue bytes and SHALL NOT ask the operator to invent a replacement identifier.

#### Scenario: Title-only creation succeeds

- **WHEN** an operator creates an Issue with a valid title and no Issue identifier
- **THEN** the result contains a system-assigned UID and human Issue key
- **AND** the new Issue is open with the authored title

#### Scenario: Duplicate titles remain distinct

- **WHEN** two Issues are created with the same valid title
- **THEN** each has a different UID and a different Issue key
- **AND** neither title is rewritten to manufacture identity

#### Scenario: Allocation exhaustion writes nothing

- **WHEN** the system cannot allocate a non-conflicting UID and key within its bounded attempts
- **THEN** creation is refused with an allocation failure
- **AND** no Issue record, directory, plan, or narrative is published

#### Scenario: Post-publication cleanup failure preserves the committed identity

- **WHEN** atomic publication commits the exact new Issue record and a later durability, verification, or cleanup step reports failure
- **THEN** creation returns the committed UID and key with an explicit warning
- **AND** the caller is not told creation failed or encouraged to retry into a duplicate Issue

#### Scenario: Unobservable publication outcome preserves recovery identity

- **WHEN** atomic publication fails and the exact commit point cannot be read or otherwise verified
- **THEN** creation is refused as publication-indeterminate with the intended immutable UID and key and `retrySafe: false`
- **AND** it does not claim zero writes, allocate around unreadable evidence, or invite a fresh blind create

#### Scenario: An indeterminate UI create cannot be submitted twice

- **WHEN** the Unlinked Changes dialog receives publication-indeterminate recovery with an assigned UID/key and `retrySafe: false`
- **THEN** that dialog preserves and displays the recovery identity and disables every further fresh-create attempt for its current mounted state
- **AND** its explicit recovery action inspects or attaches by the returned canonical UID, while closing and mounting a new dialog creates a separate fresh state

#### Scenario: Retained atomic carriers do not become allocation failure

- **WHEN** an absent-before write fails after creating the UID directory or an intent, claim, or backup carrier
- **THEN** the system preserves any carrier whose safe ownership cleanup cannot be proved
- **AND** it reports the publication-indeterminate recovery contract rather than the zero-write allocation-failure contract

### Requirement: Machine identity, human reference, aliases, and storage location have separate roles

An Issue UID SHALL be the sole authoritative identity used by new durable Issue relationships and
locks. An Issue key SHALL be a stable system-generated human reference accepted by interactive
surfaces. A slug or alias SHALL be a non-authoritative display or search convenience and SHALL NOT
determine equality, locks, relationships, or paths. Physical storage location SHALL be an internal
locator and SHALL NOT be exposed as Issue identity by the API or UI.

#### Scenario: A presentation alias does not change identity

- **WHEN** an Issue is selected through a slug or legacy alias
- **THEN** the resolved Issue carries the same UID and key as when selected through its UID
- **AND** the alias is not used as the relationship or lock identity

#### Scenario: A new durable child resource names the UID

- **WHEN** a new Execution Plan, acceptance-conditions revision, or acceptance record is published
- **THEN** the resource records its owning Issue UID
- **AND** it does not persist a key, slug, or legacy alias as owner identity

#### Scenario: Unreadable identity does not expose its storage fallback

- **WHEN** an Issue record is malformed or its recorded identity disagrees with its storage location
- **THEN** public CLI and HTTP projections redact the storage locator from summary identifiers, problem identifiers, paths, diagnostics, reasons, and divergence copies
- **AND** absolute local paths are absent while the core read remains incomplete and diagnostic

#### Scenario: Execution Plan projection does not promote an internal fallback

- **WHEN** an Execution Plan read carries an Issue storage fallback but its associated Issue summary has no verified public identity
- **THEN** the public plan `issueId` and Issue problem `itemId` use the explicit unavailable identity marker
- **AND** the response contains no storage key or physical path and does not invent a stable identity

### Requirement: Issue selectors resolve through one fail-closed catalog

Issue operations SHALL accept the canonical UID, generated Issue key, unique slug, and compatible
legacy identifier as selectors. Resolution SHALL be made against a catalog generated from the
authoritative Issue records visible to that operation. No result SHALL be chosen when a selector
matches zero Issues, more than one UID, or an incomplete catalog that cannot prove uniqueness for a
mutation.

#### Scenario: UID and key resolve the same Issue

- **WHEN** an operator addresses one Issue once by UID and once by its generated key
- **THEN** both operations resolve the same authoritative UID
- **AND** both use that Issue's actual internal storage locator

#### Scenario: An ambiguous alias is not guessed

- **WHEN** a slug or compatible alias matches more than one distinct Issue UID
- **THEN** selector resolution reports ambiguity with the candidates
- **AND** no ref order, timestamp, directory order, or case rule selects a winner

#### Scenario: Concurrent creation cannot invalidate a mutation selector

- **WHEN** a mutation resolves a unique slug or alias while another operation creates an Issue that would make that selector ambiguous
- **THEN** creation and selector resolution are serialized at the Store identity boundary
- **AND** the mutation either linearizes before the new identity is published or refuses the now-ambiguous selector without writing

#### Scenario: Raw selector text never becomes a path

- **WHEN** a selector contains traversal text, a platform separator, or a Windows device name
- **THEN** it is either matched as a declared non-path alias or rejected as a selector
- **AND** its raw bytes are never passed to the Store layout as a path segment

### Requirement: Legacy Issue identity is projected deterministically without write-on-read

A version-1 Issue SHALL receive a deterministic compatibility UID scoped by the Store's permanent
UID and its existing identifier, and a deterministic human key derived from that UID. Its existing
identifier SHALL remain a compatible alias and its existing directory SHALL remain its internal
storage location. Reading legacy identity SHALL NOT move, rewrite, or create any file, and existing
version-1 canonical bytes and digests SHALL remain unchanged.

#### Scenario: Clones agree on a legacy UID

- **WHEN** the same version-1 Issue is read in two clones of the same Store
- **THEN** both project the same compatibility UID and human key
- **AND** neither clone writes identity metadata while reading

#### Scenario: The same old identifier is Store-scoped

- **WHEN** two Stores contain version-1 Issues with the same old identifier
- **THEN** their projected UIDs differ because the Stores' permanent UIDs differ
- **AND** neither Issue is treated as a cross-Store copy of the other

#### Scenario: A legacy selector writes to the legacy storage location

- **WHEN** an allowed mutation addresses a version-1 Issue through its old identifier
- **THEN** the mutation locks by the projected UID and writes to the existing legacy directory
- **AND** no new directory named from the selector is created

### Requirement: The selector index is generated from Issue records

The system SHALL generate the UID, key, slug, alias, and storage-locator index from authoritative
Issue records for the current read snapshot. Any cache SHALL be disposable and SHALL NOT be required
for correctness. Deleting local derived state SHALL leave the next Issue read capable of rebuilding
the same selector results.

#### Scenario: Derived state can be discarded

- **WHEN** all local selector cache state is absent
- **THEN** an Issue catalog rebuilt from the same Store records resolves the same UID, key, and aliases
- **AND** no persisted map is required or repaired
