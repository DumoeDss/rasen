# Design

## Context

Both defects were observed during a real archive of an unrelated product and reconfirmed by reading and executing the current code. The relevant sources are byte-identical between the local checkout and `upstream/dev/0.1.8` (`77c860dd`), verified with an empty `git diff --stat upstream/dev/0.1.8 HEAD -- src/core/specs-apply.ts src/core/parsers/requirement-blocks.ts src/core/archive.ts src/core/archive-engine.ts`.

## Defect 1: terminal newline in generated canonical specs

### Mechanism

`extractRequirementsSection` returns `after: after.startsWith('\n') ? after : '\n' + after`. When `## Requirements` is the final section, the slice past the section is empty, so `after` becomes `'\n'`. The serializer then composes `[before, headerLine, reqBody, after].join('\n')`, and `reqBody` is already `trimEnd()`-ed, so the join contributes one newline and `after` contributes a second. `replace(/\n{3,}/g, '\n\n')` collapses three or more, so exactly two survive.

Measured on the current sources:

| Input | Current terminal newlines |
|---|---|
| Newly created skeleton | 2 |
| Existing canonical spec, `## Requirements` last, input ends with one newline | 2 |
| Existing canonical spec, input already ends with two newlines | 2 |
| Existing canonical spec with a section after `## Requirements` | 1 |
| CRLF input | 2 |
| Input with no terminating newline | 2 |

The canonical shape is `## Purpose` followed by `## Requirements`, so `## Requirements` is the last section in practice and the two-newline result is the normal case, for both created and updated specs.

### Decision

Normalize at the serializer's output edge rather than at the parser. One normalization covers every input shape — zero, one, or several terminating newlines, CRLF, and both the created and updated paths — so no case analysis about which stage contributed the newline is needed, and `extractRequirementsSection` keeps its current contract for its other callers.

Rejected: changing `after`'s promotion rule in `extractRequirementsSection`. It has other callers, the fix would still have to reason about the non-final-section case, and it would not normalize an input that already carried a trailing blank line.

### Compatibility

- Saved archive plans store `rebuilt` as a string and the engine writes that string; it does not recompute it. A plan saved by an older build applies unchanged.
- The spec drift check (`archive-engine.ts` `sourceSha256` comparisons) digests the delta source file, not `rebuilt`, so widening or narrowing the generated bytes cannot trigger `ESTALE`.
- `targetPrecondition` digests the on-disk canonical file at planning time, so an existing file that ends with a blank line still matches its own digest.
- `beforeSha256`/`afterSha256` are recorded per transaction; no source path asserts that transaction N's `beforeSha256` equals transaction N-1's `afterSha256`.
- The existing exact-content assertions in `test/core/specs-apply.test.ts` all assert that a file is *unchanged* on abort or no-op paths, so none of them pin the serializer's output.

Defect 1's only observable difference is a one-time removal of the trailing blank line the next time a delta rewrites a canonical spec that already carries one. Defect 2's observable difference is recorded under `## Risks`.

## Defect 2: ship-commit reading depends on Markdown presentation

### Mechanism

Both `src/core/archive.ts` and `src/core/archive-engine.ts` carry the same expression, matching the whole line:

```
/^\*\*Commit:\*\*\s*([0-9a-f]{7,64})\s*$/im
```

A hash wrapped in a code span does not match, so `recordedCommit` becomes `null` and the archive-owned `## Archive` section omits `**Ship commit:**` entirely — the same path a change that never shipped takes.

### Decision

Read the field in two steps instead of widening the hash pattern in place: for each `**Commit:**` line in document order, capture the value on that line, strip one matched surrounding pair of backticks, and validate the result as a 7-to-64 character hexadecimal hash; return the first value that validates, or `null` when none does. Compared with adding `` `? `` on both sides of the capture, this rejects an unmatched backtick rather than silently accepting it.

Two properties of the replaced expression are decided explicitly rather than inherited by accident:

- First readable field wins. The replaced expression required the whole line to be a hash, so `String.prototype.match` skipped an unreadable `**Commit:**` line and returned the first readable one. Reading only the first labelled line would regress a log whose header holds a placeholder and whose later line holds the real hash to no recorded commit — the defect this change removes. Multi-field logs exist in this repository (`rasen/changes/archive/2026-08-09-fix-existing-change-workspace-binding/evidence/ship-log.md:6,44`), as do placeholder header fields (`rasen/changes/archive/2026-07-09-telemetry-admin-console/ship-log.md:6`).
- A value is line-scoped. The replaced expression's `\s*` matched a newline, so a hash on the line after the label resolved, as did a value separated from the label by a non-space, non-tab character such as U+00A0. Neither reads now. The value of a one-line field is what sits on its line, matching the sibling idiom `hasReservedArchiveShipLogSection` (`src/core/archive-engine.ts:105-107`). Line endings (LF or CRLF), trailing spaces and tabs, uppercase hexadecimal digits, and a 7-character abbreviated hash read as before.

| Log | Replaced expression | `` `? `` widening | Shared reader |
|---|---|---|---|
| `**Commit:** <hash>` | hash | hash | hash |
| `` **Commit:** `<hash>` `` | null | hash | hash |
| `` **Commit:** `<hash> `` | null | hash (wrong) | null |
| `**Commit:** <hash> (dirty)` | null | null | null |
| `**Commit:**` | null | null | null |
| no `**Commit:**` line | null | null | null |
| unreadable `**Commit:**` line, then a readable one | later hash | later hash | later hash |
| two readable `**Commit:**` lines | first hash | first hash | first hash |
| `**Commit:**` with the hash on the following line | hash | hash | null |

The reader's signature is `readRecordedShipCommit(content: string): string | null`. It carries no present-versus-absent discriminator: neither call site would read one, an unreadable value continues to produce `recordedCommit: null` with no new blocker, and the archive JSON contract is unchanged. Making that distinction a typed blocker is deferred to its own change, which introduces the discriminator when it has a consumer.

### One reader, two call sites

The duplicated expression is replaced by a single exported reader consumed by both planning and finalization. Planning reads the source log into `shipLog.recordedCommit`; finalization writes the planned value and falls back to reading the staged copy only when the plan recorded none. Divergence between two readers would let a plan record one ship commit while the transaction that applies it derives another; a shared reader makes that unrepresentable for any plan saved and applied under the same reading rule. The fallback deliberately does not make it unrepresentable ACROSS rules: a plan saved before this change for a code-span log carries `null`, and the applying transaction now reads the hash and writes it into the archive section. That is the desired direction — the archive gains the true provenance, `archive.json` digests the finalized content at apply time so no digest disagrees, the saved plan is never rewritten, and Store v2 keeps reading the plan's `null` (`src/core/store/finalization/module.ts:1333`) and falling through to `HEAD` as it did before the upgrade.

## Risks

- A repository that has pinned the digest of a canonical specification outside Rasen's own contracts sees a one-time change when that specification is next rewritten. Rasen records no such cross-run digest itself.
- Widening ship-commit reading means archives that previously recorded no ship commit for a code-span log will now record one. That is the intended correction, and it cannot retroactively alter an already-published archive, whose evidence is immutable.
- A newly readable ship commit changes which commit a Store v2 `landed` finalization proves. `proveLanded` feeds `shipLog.recordedCommit` to `resolveCodeCommitCandidate` (`src/core/store/finalization/module.ts:1331-1335`), which ranks it behind an explicit `--commit` and above the execution `HEAD` (`src/core/store/finalization/reachability.ts:34-41`, flag forwarded from `src/core/archive.ts:1668`). Absent that flag, a code-backed change whose log presents its commit as a code span used to be proven against `HEAD`; it is now proven against the recorded commit and refused with `landed_commit_unresolved` when that commit does not name an object in the execution repository (`reachability.ts:78-93`) or `landed_commit_unreachable` when it is not an ancestor of the target line's code ref (`reachability.ts:155-166`). `change-finalization-outcomes` requires that priority, so proving `HEAD` while ignoring a readable ship commit was the non-conforming behavior, and the refusal is the specified outcome. The line-scoping narrowing moves the same ranking the other way — a log whose hash sat on the line after its label no longer resolves, so such a change falls back to a later readable field or to `HEAD`, which can turn a previous refusal into a pass. Planning-only changes resolve no commit (`module.ts:1325-1330`) and are unaffected.
