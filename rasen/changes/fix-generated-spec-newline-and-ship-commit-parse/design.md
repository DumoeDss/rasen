# Design

## Context

Both defects were observed during a real archive of an unrelated product and reconfirmed by reading and executing the current code. The relevant sources are byte-identical between the local checkout and `upstream/dev/0.1.8` (`77c860dd`), verified with an empty `git diff --stat upstream/dev/0.1.8 HEAD -- src/core/specs-apply.ts src/core/parsers/requirement-blocks.ts src/core/archive.ts src/core/archive-engine.ts`.

## Defect 1: terminal newline in generated canonical specs

### Mechanism

`extractRequirementsSection` returns `after: after.startsWith('\n') ? after : '\n' + after`. When `## Requirements` is the final section, the slice past the section is empty, so `after` becomes `'\n'`. The serializer then composes `[before, headerLine, reqBody, after].join('\n')`, and `reqBody` is already `trimEnd()`-ed, so the join contributes one newline and `after` contributes a second. `replace(/\n{3,}/g, '\n\n')` collapses three or more, so exactly two survive.

Measured on the current sources:

| Input | Current terminal newlines |
|---|---|
| Newly created skeleton | 2 |
| Existing canonical spec, `## Requirements` last, input ends with one newline | 2 |
| Existing canonical spec, input already ends with two newlines | 2 |
| Existing canonical spec with a section after `## Requirements` | 1 |
| CRLF input | 2 |
| Input with no terminating newline | 2 |

The canonical shape is `## Purpose` followed by `## Requirements`, so `## Requirements` is the last section in practice and the two-newline result is the normal case, for both created and updated specs.

### Decision

Normalize at the serializer's output edge rather than at the parser. One normalization covers every input shape — zero, one, or several terminating newlines, CRLF, and both the created and updated paths — so no case analysis about which stage contributed the newline is needed, and `extractRequirementsSection` keeps its current contract for its other callers.

Rejected: changing `after`'s promotion rule in `extractRequirementsSection`. It has other callers, the fix would still have to reason about the non-final-section case, and it would not normalize an input that already carried a trailing blank line.

### Compatibility

- Saved archive plans store `rebuilt` as a string and the engine writes that string; it does not recompute it. A plan saved by an older build applies unchanged.
- The spec drift check (`archive-engine.ts` `sourceSha256` comparisons) digests the delta source file, not `rebuilt`, so widening or narrowing the generated bytes cannot trigger `ESTALE`.
- `targetPrecondition` digests the on-disk canonical file at planning time, so an existing file that ends with a blank line still matches its own digest.
- `beforeSha256`/`afterSha256` are recorded per transaction; no source path asserts that transaction N's `beforeSha256` equals transaction N-1's `afterSha256`.
- The existing exact-content assertions in `test/core/specs-apply.test.ts` all assert that a file is *unchanged* on abort or no-op paths, so none of them pin the serializer's output.

The single observable difference is a one-time removal of the trailing blank line the next time a delta rewrites a canonical spec that already carries one.

## Defect 2: ship-commit reading depends on Markdown presentation

### Mechanism

Both `src/core/archive.ts` and `src/core/archive-engine.ts` carry the same expression, matching the whole line:

```
/^\*\*Commit:\*\*\s*([0-9a-f]{7,64})\s*$/im
```

A hash wrapped in a code span does not match, so `recordedCommit` becomes `null` and the archive-owned `## Archive` section omits `**Ship commit:**` entirely — the same path a change that never shipped takes.

### Decision

Read the field in two steps instead of widening the hash pattern in place: capture the `**Commit:**` line's value, strip one matched surrounding pair of backticks, then validate the result as a 7-to-64 character hexadecimal hash. Compared with adding `` `? `` on both sides of the capture, this rejects an unmatched backtick rather than silently accepting it, and it separates "the field is absent" from "the field is present but not a hash" as a byproduct.

| Field | `` `? `` widening | Two-step read |
|---|---|---|
| `**Commit:** <hash>` | hash | present, hash |
| `` **Commit:** `<hash>` `` | hash | present, hash |
| `` **Commit:** `<hash> `` | hash (wrong) | present, no value |
| `**Commit:** <hash> (dirty)` | no value | present, no value |
| `**Commit:**` | no value | present, no value |
| no `**Commit:**` line | no value | absent |

The `present`/`absent` distinction is computed but not acted on in this change: an unreadable value continues to produce `recordedCommit: null` with no new blocker, so the archive JSON contract is unchanged. Making that distinction a typed blocker is deferred to its own change, and this shape means that change will not have to revisit the parser.

### One reader, two call sites

The duplicated expression is replaced by a single exported reader consumed by both planning and finalization. Divergence between them would let a plan record one ship commit while the transaction that applies it derives another; a shared reader makes that unrepresentable.

## Risks

- A repository that has pinned the digest of a canonical specification outside Rasen's own contracts sees a one-time change when that specification is next rewritten. Rasen records no such cross-run digest itself.
- Widening ship-commit reading means archives that previously recorded no ship commit for a code-span log will now record one. That is the intended correction, and it cannot retroactively alter an already-published archive, whose evidence is immutable.
