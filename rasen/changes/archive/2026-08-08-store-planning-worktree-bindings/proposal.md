## Why

Scope routing already refuses a project mutation that cannot prove a verified planning worktree, and layout migration already produces the project partitions that mutation would write into. Nothing in between exists. There is no way to create the Store planning worktree the guard demands, no way to bind it to the execution checkout where the code is written, and no way to prove that either side is still the worktree the binding named. Today the only planning worktree Rasen accepts is one an operator assembles by hand — a `git worktree add` plus a hand-written `.rasen/planning-line.json` — and the guard admits it on the strength of that file alone, without checking that the target line exists, that the marker agrees with anything else, or that the worktree is still the one the marker describes.

Two more gaps make the layout v2 Store unusable in practice. A target line is the key layout v2 partitions Archive by and the fact `PlanningScopeId` is derived from, yet the only thing in the portfolio that writes a target-line catalog is the migration mapping file, so a Store cannot gain a second release line after it is migrated. And a session freezes its planning root and its execution root but not the pair, so a command inside a session still cannot tell whether the Store worktree it is writing to is the one this Change was started in.

Preparing that pair means creating Git worktrees in two repositories, and that is the first place in this portfolio where Rasen mutates Git on the user's behalf. Mutation therefore goes through an immutable plan and a token revalidated against Git OIDs under a semantic lock, the allowed Git verb set is closed and non-destructive, and every uncertain fact — an unresolvable ref, a disagreeing marker, a dirty tree, an unmerged branch — refuses rather than repairs itself.

## What Changes

- Add `StoreTargetLines` with `add` / `set-ref` / `list` / `show` / `resolve`: a stable `targetLineId` whose Store and per-project code refs are mutable locators, resolved to concrete refs and commit OIDs at use time. Changing a locator SHALL NOT change the identity, and no command infers a target line from a branch name.
- Add a `StoreWorkspaceModule` with `plan` / `apply` / `describe` / `planCleanup` / `applyCleanup`, surfaced on the planning seam as `planChangeWorkspace` / `applyWorkspacePlan`. `plan` is read-only and total; `apply` consumes only a content-addressed token and re-reads neither the current directory nor the selectors that produced the plan.
- Derive the planning and execution `WorktreeInstanceId` from canonical Git repository and worktree identity supplied by the Git adapter, and complete the `WorkspacePairId` when the pair's single Change instance exists. A prepared workspace is `unbound` until exactly one Change is created in its planning worktree, then `bound`; a second Change creation in the same planning worktree is refused.
- Record the binding in four carriers with explicit authority: the Change's committed v2 identity block is the portable half and needs no schema change; the planning-worktree marker and the execution-worktree association are per-worktree local locators; the machine workspace registry is a rebuildable index that is re-verified before every use and is never authority on its own. A missing index entry is repaired from the markers and Git; a disagreeing one fails closed.
- Bind Git OID preconditions into the plan — the target line's Store ref and code ref, and the HEAD of every reused worktree — and create new worktrees from the recorded OID rather than from the ref name, so a ref that moves between plan and apply invalidates the plan instead of silently retargeting it.
- Define the four semantic lock keys the accepted design requires — scope, change, workspace, and integration — as owner-aware machine-root locks acquired in a fixed order with bounded retry. Contention retries; a semantic conflict never does. Workspace preparation and cleanup take the scope and workspace locks; the change and integration locks are published for the finalization owner.
- Refuse rather than repair on every binding disagreement, with a closed taxonomy: `planning_execution_binding_missing`, `planning_execution_binding_mismatch`, `workspace_binding_ambiguous`, `workspace_marker_conflict`, `target_line_mismatch`, `target_line_ref_unresolved`, `workspace_ref_mismatch`, `workspace_dirty_tree`, `workspace_destination_exists`, `workspace_already_bound`, `workspace_plan_stale`, `workspace_lock_unavailable`, and `workspace_cleanup_unsafe`.
- Preparation never moves a ref, a HEAD, or a working tree. Reusing an existing worktree that is on a different ref refuses with `workspace_ref_mismatch` rather than switching it, and no path outside the two planned worktree roots is written.
- Freeze the complete pair into the session: Store `planningWorktree`, `executionWorktree`, `changeInstanceId`, and `workspacePairId` alongside the existing roots, with the context file version raised to 2. A command inside a session uses the frozen pair and fails closed when the live worktree disagrees, instead of re-deriving the pair from the working directory.
- Report the pair in `rasen context --json` and its human form: both worktree roots, their instance ids, checked-out refs and HEAD OIDs, the target line, the Change instance, the pair id, the binding state (`unbound`, `prepared`, `bound`, `drifted`), and every verification finding — as inert locators that confer no mutation authority.
- Add a cleanup protocol that is itself plan/apply and removes only what it can prove is safe: the worktree must be one the pair recorded, on the ref the pair recorded, clean, with every commit on its branch reachable from the recorded integration or target ref, with no live session referencing it and no lock held. Removal uses `git worktree remove` without `--force`. Cleanup never deletes a branch, never merges, never resets, and never touches the Store integration checkout, the code repository's main checkout, the Change directory, the Archive, or another pair's state.
- Close the Git verb set with a source guard: the workspace adapter may call `worktree add`, `worktree remove`, `worktree prune`, and read-only plumbing, and may never call `merge`, `rebase`, `reset`, `checkout`, `switch`, `branch -d`/`-D`, `push`, `fetch`, `clone`, or `worktree remove --force`.
- Add `rasen store workspace plan|apply|show|cleanup` and `rasen store target-line add|set-ref|list|show`, each with `--json` whose content matches the human form, and each printing pathspec-scoped commit suggestions while staging, committing, fetching, and pushing nothing. The workspace group is a `store` subcommand rather than a top-level one because `workspace` is a retired top-level command name that a test keeps dead, and because a workspace pair is Store content.
- **BREAKING (session context):** the session context file version is raised from 1 to 2 so the frozen pair is a first-class shape rather than an optional field on a strict schema. A session started by an earlier build and still running when the binary is upgraded will report its context as an unsupported version — the plain report the capability already requires — instead of silently losing the pair. The repair is to restart the session; the file is machine-local and is removed when the session ends, so nothing durable is affected.
- **Behavior tightening (not a capability loss):** a planning-worktree marker is no longer sufficient on its own. It must declare the resolved Store, project, and target line, its target line must resolve to an existing Store ref, and its worktree identity must re-derive from the live repository. A healthy hand-assembled pair keeps working and is indexed on first use; an inconsistent one that previously passed now fails closed.

## Capabilities

### New Capabilities

- `store-target-lines`: stable target-line identity with mutable Store and per-project code-ref locators, explicit authoring, resolution to concrete refs and OIDs, and the `target_line_mismatch` gate that stops a Change from being re-pointed at another line.
- `store-planning-worktree-bindings`: the immutable workspace plan/token/revalidation contract, planning and execution worktree identities and their pairing, the four binding carriers and their authority order, the conflict taxonomy, the semantic lock protocol, the non-mutating preparation rule, the closed Git verb set, the context projection of the pair, and the safe cleanup protocol.

### Modified Capabilities

- `session-runtime-context`: purely additive. A session that plans in a Store and executes in a project checkout freezes the complete worktree pair — both roots, both worktree instance ids, the Change instance, and the pair id — and every command inside the session uses that frozen pair and fails closed on disagreement rather than re-deriving it. The context file version becomes 2.

## Impact

- Adds `src/core/store/workspace/**` (module, plan, apply, cleanup, identity, binding, registry, locks, diagnostics, adapters) and `src/core/store/target-lines.ts` beside the existing planning seam, and wires `planChangeWorkspace` / `applyWorkspacePlan` onto `StorePlanning` so the planning-worktree verification in `src/core/store-planning/internal/resolver.ts` consumes real evidence instead of marker presence.
- Adds one machine-root family, `<dataDir>/planning-workspaces/` (plans, the binding index, and locks). Neither Git repository stores a plan, a token, a lock, or an index entry, and no command in this change stages, commits, fetches, or pushes.
- Raises `RUNTIME_CONTEXT_VERSION` to 2 in `src/core/session-runtime-context.ts` and extends the Store planning arm and the project execution arm with the frozen pair; extends the `rasen context` payload in `src/commands/context.ts`.
- Adds `rasen store workspace` and `rasen store target-line` to `src/commands/`, `src/core/completions/command-registry.ts`, and all three locale trees (`src/locales/{en,ja,zh-cn}.json`).
- Adds target-line, identity, plan/token, lock, conflict, freezing, context, and cleanup unit suites; a two-line concurrent end-to-end journey; a Git-verb source guard; and Windows/POSIX path-identity, alias-path, Unicode, and long-path fixtures.
- Depends on `store-layout-v2-migration` for the partitions and catalogs a prepared workspace writes into, on `store-planning-scope-routing` for the scope seam, and on the Foundation identity and layout contracts. Finalization outcomes and Archive v2 remain closed — this change does not unlock `store_v2_finalization_unavailable` and performs no merge into a Store integration ref. Store Issues and management aggregation, read-caller migration, and the doctor/CI target-line consistency gates remain later slices.
- Known remaining gap, deliberately not absorbed: `rasen store setup` still creates a Store declaring no layout version, so a brand-new Store is born legacy-flat and has nothing to migrate. Target-line authoring here removes the second half of that dead end, but minting layout v2 at Store creation belongs to `store-bootstrap` and is outside this change's scope boundary.
