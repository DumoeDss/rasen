## Executive Summary

Slice A replaces the canvas's three single-selection scalars
(`selectedStageId` / `selectedConnectionId` / `selectedDeclarationId`) with a
set-based selection model in which **React Flow owns the interaction truth**
(`node.selected` / `edge.selected`, driven by its built-in Shift+drag box-select
and Ctrl/Cmd+click augmentation) and the page keeps **one derived mirror**
(`CanvasSelection { nodeIds, connectionIds }`) that every panel reads. Singleton
selections keep today's exact panel behavior; multi-selections render a new
summary panel whose independently-useful capability is multi-delete with
parallel-pair co-deletion. The model is deliberately shaped as the consumption
contract for children B/C/D (subgraph extraction, loop inference, frontier
inference all consume the node-id set).

## Problem Statement

The v2 canvas editor currently has no multi-select at all. Selection is three
mutually-exclusive single scalars (`PipelineCanvasPage.tsx:148/152/154` at
`74568906`): one root node (also serving v1 stages), one connection, one
declaration. There is no box-select wiring, no `onSelectionChange` subscription,
and no panel that can represent "several things are selected". The immediate
user-visible costs: bulk cleanup of a draft means N single deletes; and the
portfolio's whole reason to exist — the author box-selects a region and says
"package this into a reusable block" (the round-one user wording:
框选「打成复用块」) — has no selection substrate to build on. Children B/C/D
(subgraph extraction, back-edge loop inference, parallel-frontier inference) all
consume a selected-node set that does not exist yet.

There is also a latent divergence today: React Flow's *own* internal selection
(`node.selected`, already active because `elementsSelectable` is set and
Shift+drag box-select is React Flow's default `selectionKeyCode`) advances
independently of the page scalars. A user can box-select five nodes and press
Delete **today** — the `onNodesChange` remove loop happens to handle the batch —
while the properties panel still shows whatever single node the scalars last
held. Two unsynchronized selection truths is exactly the drift class this repo's
"one home" discipline exists to prevent.

- V4. React Flow v12 defaults (`@xyflow/react` ^12.3.6, per

  `multiSelectionKeyCode` = platform-aware (Meta on macOS, Control elsewhere),
  `deleteKeyCode` = `'Backspace'` (repo already passes

**Declared assumptions (not branch-writable / no answer would flip the design):**

- D1. Declaration selection stays a single scalar. The declaration editor edits
  exactly one declaration; set semantics there is noise, and `DeclarationsPanel`
  is untouched by slice A.
- D2. `markDraftChanged()` continues to leave canvas selection alone (it clears
  issue markers only). Selection surviving edits is desired; it is removed ids
  that must be pruned, at the mutation sites that remove them.
- D3. View mode is unaffected: view-mode ReactFlow already allows
  zoom/pan/fit/select read-only (spec :250/:265); slice A wires no selection
  panels in view mode, same as today.
- D4. This stage writes no run-state and no code; the deliverable is this doc.

## Approaches Considered

### Approach A: Minimal add-on (keep scalars, bolt multi-delete onto React Flow internals)

Keep the three scalars as the panel state; subscribe to `onSelectionChange`
only inside the delete path so box-select + Delete works. Fewest files touched,
ships fastest.

- Pros: smallest diff; no test churn in panel-selection assertions.
- Cons: leaves two selection truths permanently divergent (panels vs canvas
  highlight); no panel can ever render a multi state, so child B would have to
  re-lift the whole model anyway; the node-XOR-connection exclusivity logic
  stays and fights the set semantics React Flow natively produces.
- Completeness: 4/10 — defers the actual substrate the portfolio needs.

### Approach B: React Flow-owned selection, page derives (recommended)

React Flow's `node.selected`/`edge.selected` is the single interaction truth
(its built-in Shift+drag box-select and Ctrl/Cmd+click augmentation drive it).
The page holds one derived mirror `CanvasSelection { nodeIds, connectionIds }`
updated by `onSelectionChange` (user actions) and by programmatic replacers
(gesture handlers, issue navigation); `recomputeFlow` stamps `selected` back
onto rebuilt nodes from the mirror so mutations no longer visually deselect.
Panels derive their mode from the mirror's counts.

- Pros: one truth; box-select free; singleton panel behavior preserved by
  derivation; the mirror is exactly the consumption contract B/C/D need;
  deletes the hand-rolled XOR handlers instead of extending them.
- Cons: every one of the ~16 scalar write sites must be migrated (enumerated
  under Recommended Approach); existing tests asserting scalar behavior need
  updating.
- Completeness: 9/10.

### Approach C: Page-owned Set, mirrored into React Flow nodes (two-way sync)

Page owns the sets and writes `selected` onto the nodes it passes down; React
Flow change events are folded back into the sets.

- Pros: most explicit control; testable without React Flow internals.
- Cons: two-way synchronization is precisely the drift class constraint 2 and
  draft.ts's vocabulary comments warn about ("four independent encodings …
  drifting apart"); strictly more code than B for less fidelity.
- Completeness: 6/10.

## Recommended Approach

**Approach B.** Concretely:

### B1. State and derivations (page)

Replace `selectedStageId` + `selectedConnectionId` with:

```ts
// draft.ts (one home): the canvas selection model
export interface CanvasSelection {
  nodeIds: ReadonlySet<string>;
  connectionIds: ReadonlySet<string>;
}
export const EMPTY_CANVAS_SELECTION: CanvasSelection = { ... };
export function selectionPanelMode(s: CanvasSelection): 'empty' | 'node' | 'connection' | 'multi';
export function singletonNodeId(s: CanvasSelection): string | null;
```

- `selectedDeclarationId` stays a scalar (D1).
- Page memos replace today's three: `primarySelectedNodeId` (=
  `singletonNodeId`) feeds `selectedV2Node`/`selectedStage` and the field-issue
  memos unchanged in behavior — **singleton selection keeps today's exact panel
  experience, including `key={id}` remount semantics**;
  `primarySelectedConnectionId` feeds `V2ConnectionPanel`;
  `selectionPanelMode` picks which panel renders.
- v1 compat: v1's `StagePanel`, `renameSelectedStage`, and `patchStage` paths
  consume `primarySelectedNodeId`. v1 multi-delete already works (the v1 remove
  branch loops `removeStage`); v1 has no connection panel to migrate.

### B3. Box-select wiring (CanvasFlow)

Pin the defaults explicitly so behavior is config-visible and drift-proof:
`selectionKeyCode="Shift"`, leave `multiSelectionKeyCode` at its platform-aware
default (Control on Windows — verified V4), `selectionOnDrag` stays `false`,
`deleteKeyCode` unchanged. Pass `onSelectionChange` through `CanvasFlow`'s
props alongside the existing handlers it replaces.

### B4. Multi-delete (the independently-useful capability)

New pure batch helper in draft.ts (model owns the rules, per constraint 2):

```ts
export interface V2NodeRemovalPlan {
  next: WirePipelineDefinitionV2;
  removedIds: string[];              // actually deleted
  refused: { id: string; reason: string }[]; // per-refusal model messages
}
export function removeV2Nodes(def: WirePipelineDefinitionV2, ids: ReadonlySet<string>): V2RemovalPlan;
```

- Pair-aware routing: a selected `FanOut` routes through `removeParallelPair`
  (its `Join` goes with it whether or not the Join was also selected; a
  selected `Join` whose FanOut was not selected is refused with the model's
  existing paired-deletion message).
- All other refusals (Gate target, last parallel member, read-only kind)
  surface as `{id, reason}` entries reusing `removeV2Node`'s existing message
  strings — no new vocabulary.
- **Best-effort, not atomic**: eligible nodes delete; refusals are collected.
  The page shows **one** summary toast ("Deleted 5 · 2 refused: …") instead of
  N toasts. Atomicity is deliberately deferred — child B's cut is where
  all-or-nothing semantics become load-bearing.
- The page's remove path calls this once per delete batch, prunes
  `selection.nodeIds` by `removedIds`, then `recomputeFlow` + `markDraftChanged`
  as today.
- v1 branch keeps its existing `removeStage` loop (already batch-capable).

### B5. Panels

- `selectionPanelMode === 'node'` → `V2NodePanel` (unchanged component);
  `'connection'` → `V2ConnectionPanel` (unchanged); `'multi'` or mixed →
  new small `V2SelectionPanel` in the same right-column slot: selection counts
  and kind breakdown, a Delete-selection button invoking the same batch path,
  and nothing else. No disabled previews of future actions (dead UI; B adds its
  own affordance when it lands).
- `PalettePanel`, `DeclarationsPanel`, `IssuesDrawer` untouched.

### B6. Forward-compatibility contract for children B/C/D

The public contract slice A hands forward is exactly `CanvasSelection` —
B (subgraph extraction) consumes `nodeIds` and derives its severed-edge cut
from the draft itself (edge *selection* is not part of B's input); C (loop
inference) and D (frontier inference) consume `nodeIds`/topology. Slice A must
therefore keep `selection` a first-class page state (not an incidental local)
and must not special-case "exactly two" or any B-shaped assumption into the
model.

### B7. recomputeFlow and durable positions — the flagged question, answered

Slice A needs the **selection-carry** (B2 #16) but does **not** need durable
node positions: selection is id-keyed, box geometry is read at gesture time,
and nothing in A places nodes manually. Position non-durability (a drop
coordinate discarded on the next keystroke) remains a real, known defect —
out of A's scope, flagged for whichever later slice first wants manual
placement or drag-stable visuals. Note the carry makes an existing annoyance
*visible*: today every mutation silently deselects; after A, selection
visibly persists, which is the correct behavior.

## Success Criteria

- Shift+drag draws a selection box and selects multiple nodes/edges; Ctrl
  (Win) / Cmd (mac) + click augments — verified in a real browser via the
  throwaway-CDP recipe (never the user's daily Chrome).
- Singleton behaviors are byte-for-byte today's: one node → `V2NodePanel`
  opens with field-issue focus; one connection → `V2ConnectionPanel`; issue
  click → selects that stage and opens its panel.
- Multi state renders `V2SelectionPanel`; its Delete removes all eligible
  nodes; a FanOut deletes **with** its Join; Gate-target / last-member /
  read-only refusals produce **one** summary toast naming them; selection is
  pruned of removed ids.
- Selection visually survives non-destructive mutations (add node, patch
  contract, rename follows to the new id).
- `git diff <base> -- src/core/pipeline-registry/` empty; commits use narrow
  pathspecs; UI tests run via the `packages/ui` vitest config with the count
  cited; no save/reload flow appears in verification (constraint 5).
- New/updated tests: draft.ts removal-plan unit tests (pair routing, refusals,
  mixed batches); component tests driving `onSelectionChange` with synthetic
  sets asserting panel modes and pruning; a selection-carry regression test
  (mutate → `node.selected` persists). Box-select geometry itself is not
  jsdom-testable (no layout) — handler-contract tests + the real-browser check
  cover it.

## What Makes This Cool

The substrate the user actually asked for — "I imagine drawing a box around
these nodes and turning them into a block" — turns out to already be half-alive
inside React Flow, invisible to the app. Slice A is less "build multi-select"
than "stop suppressing it": delete the hand-rolled XOR scalars, let the
interaction library's native selection become the truth, and the box the user
draws becomes the input to every inference gesture that follows.
