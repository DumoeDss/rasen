## Context

This change is the authoritative executor the durable agent session host explicitly defers to. The host's own capability spec (`rasen/specs/durable-agent-session-host/`) carries the requirement "Host outcomes never become canonical execution or trust authority ... A host result SHALL remain untrusted execution input until a later authoritative executor validates and commits it", and its design Decision 5 states "This is deliberately weaker than Action exactly-once execution ... The next child adds that authority." This change is that next child.

The deterministic Run machinery it consumes already exists and is specified. Verified in this worktree at HEAD `5f33457a` (the seed's `0f7eda09` anchors were re-checked and still hold; HEAD has moved forward only through closure archive and host review work, none of which altered the seams below):

- The canonical Run Facade (`src/core/change-run/facade.ts`) exposes `start | resume | complete | inspect | control` under a `RuntimeMutationContext { deliveryMode: 'grant' | 'defer' }`. The Facade runtime (`src/core/change-run/internal/facade-runtime.ts:214-420`) grants or defers actions and returns the granted action set; `complete` is the mutation an executor uses to commit a granted Action's result. Error codes already include `record_version_conflict`, `receipt_conflict`, and `workspace-scope-mismatch` (`facade.ts` `ChangeRunRuntimeErrorCode`), so committed-frontier resume, completion-binding mismatch, and wrong-workspace failure all have typed homes.
- `RecordVersion` is a branded monotonic type (`src/core/change-run/contracts.ts:16`); a `complete`/`control` request carries `expectedRecordVersion` (`contracts.ts:436`, `:792`), so atomic Record mutation under compare-and-swap is already the contract the transactional-integrity mechanism composes with.
- Granted actions carry `deliveryState: 'admitted_undelivered' | 'granted' | 'closed'` (`contracts.ts:601`), and the receipt validator already requires every executable receipt Action to match a granted ActionView in the same Run (`contracts.ts:1205-1214`). The executor therefore receives a frozen, validated, granted ActionView and must only execute and complete that exact object.
- The durable EvidenceStore is `src/core/change-run/internal/evidence-store-fs.ts` (`createFilesystemEvidenceStore`, `BoundedEvidenceStore`, with integrity/path-safety and budget enforcement) and `src/core/change-run/internal/evidence.ts` (`EvidenceStore`, `BoundedEvidenceStore`, `createInMemoryEvidenceStore`). `src/commands/pipeline.ts` already stages transport uploads through a `HostEvidenceWriter` before the Facade receives refs (`pipeline.ts:1871`, `:1975`, `:2060`); the executor generalises that staging into the authoritative completion path.
- The session host is `createSessionHost` (`src/core/session-host/host.ts:300`) with `closeDurableProcess` (`host.ts:696`) and its two release paths (observation `:711-714`, receipt `:715-721`), the `receiptAuthorizesRelease` gates (`host.ts:490`, `:573`, `:717`, `:1446`), the terminal-persistence declaration gate (`host.ts:767`), and `toHostedProcessTerminal` (`host.ts:652`, which hardcodes `emptiness: 'unproven'`). The host already returns `turn-outcome-unknown` for an ambiguous interrupted turn and classifies a dead generation as `interrupted` (host design Decision 5); that is the hook the executor maps to `execution-lost`.
- The ProcessScope seam and the shipped best-effort tiers are the executor's hosted backend: `receiptAuthorizesRelease` (`src/core/session-host/process-scope.ts:222-228`), `TerminationReceipt.state` = `closed | retained | uncertain | declared-unproven` (`process-scope.ts:142-143`), `DeclaredUnprovenReceipt` (`:116`), and the single selection point `createHostedProcessScope` (`src/core/session-host/process-capsule/hosted-process-scope.ts:22-31`: darwin+linux to POSIX best-effort, win32 to win32 best-effort, every other platform to the legacy capsule). Exactly-once activation is enforced at `src/core/session-host/process-authority/process-scope-adapter.ts:181`. Production construction is `createHostedProcessScope()` at `src/core/management-api/router.ts:639` and `createSessionHost` at `router.ts:642`.
- The runtime/adapter axis is already a registry: `rasen/specs/runtime-adapter-registry/` declares dispatch-capable runtimes (claude, codex) and a host x target route table (`native | exec-bridge | legacy-fallback`). Per Architecture Replan 4 this dispatch-topology axis is distinct from the process-authority axis this change's backend roster adds.

The two Step 1 obligations (Direction locked decision 11, relayed via `planning-context.md` and the Linux provider's Step 1 ledger) bind this change verbatim: typed `execution-lost` plus committed-frontier resume, and the `durable: daemon-lifetime` declaration surfaced through the capability matrix. Locked decision 12 sets the threat model ("we get it wrong") and retires producer signing, private-key custody, byte-reproducibility-as-provenance, and TOCTOU hardening from new acceptance, while explicitly preserving fail-closed typed uncertainty, capability honesty, actor separation, containment of our own workers, and transactional evidence integrity. Locked decision 13 parks the kernel-enforced authority crates whole to the upgrade path, so the hosted backend consumes the shipped best-effort tiers and declares `exactCancel: false` / `scopeEmptyProof: false`.

## Goals / Non-Goals

**Goals:**

- One authoritative executor that consumes granted frozen Actions, runs them through real Sessions on a declared two-backend roster, and completes them into the canonical Run with transactional integrity.
- A queryable OS-by-backend capability matrix, computed from declarations, visible before start, that decides what each driver face may do and that returns typed `authority-unavailable` instead of silently rerouting.
- Typed `execution-lost` on daemon/launcher death with resume only from the last committed Record frontier, and an honest per-platform receipt shape (Windows zero-orphan via the cutover's `KILL_ON_JOB_CLOSE` chain; Linux/macOS declared orphan risk with `execution-lost` typing proven instead).
- Authoritative, program-enforced per-invocation session reuse/handoff/touch/retire policy that retires the `ecp-change-run-runtime` placeholder clause.
- Driver-face same-Run parity against the matrix across the interactive launcher, bare CLI, Management API, Canvas, and daemon, with a headless driver independent of the interactive launcher.
- Real-backend attribution of the complete fact set to one canonical Run/Action, with the registry staying a host-lifecycle reader.

**Non-Goals:**

- The cancel/restart/ack-loss fault matrix at depth (slice acceptance 4's full proof surface) is owned by the downstream `ecp-session-policy-and-control-parity` child; this change owns only the `execution-lost` typing and committed-frontier resume half of acceptance 4 plus the resumability that parity consumes.
- The self-hosting toy-Change proof (acceptance 7) is the operator-owned downstream `ecp-session-self-hosting-vertical-proof` child. This change leaves the seam (the executor is what that proof drives) and does not design, select, or scope the toy Change.
- Kernel-enforced exact cancel, exact scope-empty proof, or non-escapable authority (upgrade path per decision 13); reattach, identity revalidation, or cross-daemon scope recovery (decision 11); the `prepared -> published -> activate` three-phase protocol (criterion 4, upgrade path).
- Producer signing, private-key custody, byte-reproducibility-as-provenance, or TOCTOU path-hardening as new acceptance (retired by decision 12). ECP-6's archived Ed25519 implementation is not rolled back and not extended into the producer.
- Cross-child worker reuse (`worker-reuse-config`, `worker-reuse-orchestration`), portfolio delivery, the ECP-8 release truth audit, the single clean-branch PR, and any 0.3.0 Issue/Dispatch/Execution-Plan work.
- Modifying the durable session-host registry record shape into a completion store, or modifying the host capability spec headings/scenarios (consumed as an immutable seam).

## Decisions

### D1: The executor is the single authoritative seam between the Facade and the host

The executor owns exactly the gap the host spec names: it takes a granted frozen Action from the canonical Run Facade, drives one real Session through the session host (hosted backend) or through the host tool's own worker facility (in-tool backend), and completes the Action back into the canonical Record through the Facade's `complete` mutation. It rebuilds no authority: the Action, invocation, effect, workspace, profile, adapter, and Record version are read from the granted ActionView and the committed Record, and any mismatch fails closed with the existing `receipt_conflict`, `workspace-scope-mismatch`, or `record_version_conflict` codes. The host stays a lifecycle/transport layer whose outcomes are untrusted execution input; the registry stays a host-lifecycle reader. Alternative considered: letting each driver face (CLI, Management API, Canvas, daemon) complete Actions directly into the Facade was rejected because it would re-create the implicit-launcher-as-worker-manager problem this change exists to remove and would scatter the transactional-integrity and execution-lost rules across every face.

### D2: Two declared backends; the matrix is the single source

The 0.2.0 backend roster is exactly two declared tiers, computed into one OS-by-backend capability matrix:

| Backend | OS | Owns worker | durable | headlessDriver | exactCancel | scopeEmptyProof | daemon/launcher death |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `in-tool` | all three | host tool (Claude Code / Codex) | false | false | n/a (no claim) | n/a | typed `execution-lost` on launcher death |
| `hosted` best-effort | all three (POSIX group on linux/macos; Job on win32) | rasen daemon | `daemon-lifetime` | true | false | false | scope dies with daemon; in-flight Action `execution-lost`; Windows zero-orphan via `KILL_ON_JOB_CLOSE`, linux/macos declared orphan risk |

The kernel-enforced tier is not a 0.2.0 backend (decision 13). `in-tool` is honest about what it is not: it declares durable false, headless false, and makes no exact-termination claim, and that limitation is a declared matrix fact visible before start, not an after-the-fact explanation. The "in-tool backend's actual commit is performed by the LEAD-invoked `rasen` CLI process" fact from the slice spec is recorded in run-state as a fact, not a trust semantic. The two axes the matrix joins - the runtime-adapter-registry's dispatch topology (`native | exec-bridge | legacy-fallback`) and this change's process-authority backend tier - stay distinct (Architecture Replan 4); the matrix does not collapse them.

### D3: The capability matrix is computed, queryable, and the sole "when capability allows" oracle

The matrix is a computed `ExecutionCapabilityMatrix` value, not prose. It is built by enumerating {linux, darwin, win32} x {in-tool, hosted-best-effort} and reading each backend's declaration plus current-platform availability; it exposes, per cell, the declared capability facts (`durable`, `headlessDriver`, `exactCancel`, `scopeEmptyProof`, `usageAttribution`) and a typed availability verdict (`available | authority-unavailable | <typed reason>`). Every driver face queries the same matrix to decide start/resume/cancel/inspect; "when capability allows" in slice acceptance 6 means "the matrix cell is `available`", nothing else. A `hosted` request on a platform whose hosted tier cannot serve it returns typed `authority-unavailable` and the executor SHALL NOT fall back to `in-tool`; `in-tool` is selected only by explicit request or an explicit default that the matrix showed the user before start. On a platform where only `in-tool` is available, the absence of a headless driver is a declared, pre-start-visible boundary, not a defect. Alternative considered: a prose support table in docs was rejected because it is exactly the "documentation assertion" acceptance 6 forbids and because it cannot be queried by the driver faces.

### D4: execution-lost is wired at Action-outcome reconciliation, not in the host or a provider

The host already returns `turn-outcome-unknown` for an ambiguous interrupted turn and marks a dead generation `interrupted` without resending input (host design Decision 5); the win32 hosted tier's `transportLost` latch and the POSIX scope's daemon-lifetime posture already mean a dead daemon leaves no controllable scope. The executor composes those facts into the typed `execution-lost` outcome on the Action: when the host reports a lost generation with an unfinished request (hosted backend), or when the launcher process disappears (in-tool backend), the in-flight Action is classified `execution-lost` - a typed outcome distinct from generic uncertainty and from a workload failure - and the Run is resumed only from the last committed Record frontier via the Facade, with no reattach and no identity revalidation (decision 11). The wiring lives in the executor's reconciliation of host outcomes to Action outcomes, not in the host or a provider, because Run/Record outcome typing belongs to the executor with session-host cooperation (this is the Disagreements-item-5 routing the seed records). Receipt shape is honest per platform (decision 13): Windows proves zero-orphan daemon-death teardown through the cutover's receipted `KILL_ON_JOB_CLOSE` chain; on Linux/macOS the daemon-death orphan risk is a declared known limitation and the receipt proves `execution-lost` typing plus "the uncommitted frontier stays uncommitted", not zero orphans.

### D5: Transactional completion integrity = complete-set publish plus re-read/re-verify before atomic Record mutation

Completion integrity is transactional, not cryptographic (decision 12). The mechanism has three composable parts, all built on machinery that already exists:

1. The frozen Action authors the evidence contract - the complete set of evidence objects a completion must publish. The executor's evidence writer verifies that the complete set is present and well-formed before it publishes any of it to the durable EvidenceStore; a partial set is not published as if complete.
2. The Facade's `complete` mutation re-reads the evidence set from the durable EvidenceStore and re-verifies integrity, completeness, and binding before any Record mutation. The completion claim binds Action id, invocation id, workspace revision, and ActorRef; a claim that does not bind to the granted ActionView fails closed (`receipt_conflict`).
3. The Record mutation itself is atomic under the existing Record-version compare-and-swap (`expectedRecordVersion`); a mid-publish crash leaves a partial evidence set that the re-read completeness check fails, so a later completion is never fooled into treating a half-set as complete.

No signing private key is minted, held, or accepted anywhere in this path (decision 12). ECP-6's archived Ed25519 contract is not rolled back; this change simply does not extend it into the producer. Alternative considered: re-introducing a producer signature was rejected because the attacker it would defend against (a forger who can also just edit the local Run Record) is the same party the mechanism would protect against, which is decision 12's stated rationale.

### D6: Session-reuse policy is authoritative here and retires the ecp-change-run-runtime placeholder

`ecp-change-run-runtime` records a `session` block (`reuse`, `handoffTokenLimit`, `reuseRoundLimit`, and the additive `sessionReuseAuthored`) on committed agent actions and explicitly stamps the limit values `'default'` placeholder "until a slice defines its authoritative source." This change is that slice. The authoritative source is the frozen Action's authored `sessionReuse` scope (preserved verbatim through `sessionReuseAuthored`) resolved against a declared executor policy block carrying `authored | definition | default` provenance: `never` forbids reuse; `same-invocation` permits reuse only within the same frozen invocation/role/workspace/backend-authority; the handoff token limit, reuse round limit, and touch/retire policy carry traceable source, default, and provenance and are enforced by the executor before a Session is reused. An over-limit or authority-incompatible reuse request produces an auditable handoff or retire, never a silent reuse. This is per-Run, per-invocation session reuse at the executor seam and is deliberately distinct from the cross-child worker reuse owned by `worker-reuse-config` and `worker-reuse-orchestration`; those specifications are not modified. The placeholder requirement heading in `ecp-change-run-runtime` is referenced by name, not renamed, so no scenario is implicitly deleted.

### D7: Driver-face parity unifies on one projector/control contract and the matrix

Every driver face - the Claude/Codex interactive launcher, the bare CLI, the Management API, Canvas, and the daemon - consumes the same canonical projector and the same control contract to start/resume/cancel/inspect a Run, and consults the same capability matrix (D3) to learn whether the combination is available. The headless driver (daemon-driven, hosted backend) does not depend on the interactive launcher surviving; the in-tool backend's launcher dependence is itself a declared matrix fact. No face maintains a second Run or Session truth. This realises slice acceptance 6's "all planes consume the same projector/control contract; driver switching does not duplicate Run or Session truth."

### D8: The registry stays a host-lifecycle reader; completion truth lives only in the canonical Record

The durable session-host registry (`rasen-session-host-registry/2`) continues to record only host lifecycle facts - stable Session identity, backend identity, canonical cwd, lifecycle state, generation, request/result digests, and recovery diagnostics - and the executor writes completion (result, evidence references, usage/cost, ActorRef binding) only into the canonical Record through the Facade. This composes with the host's existing "Host outcomes never become canonical execution or trust authority" and "Registry records lifecycle rather than sensitive execution content" requirements; the registry record shape is not extended with completion truth, and no second completion source is created.

### D9: The self-hosting seam is left, not designed

The executor is the execution path the later `ecp-session-self-hosting-vertical-proof` child drives to take a non-ECP toy Change from start to delivery-ready. That child is operator-owned and later; this change does not select the toy Change, pick its backend/platform, or design its evidence shape. The capability the proof will consume - frozen-Action consumption, real Session execution, transactional completion, resumability - is exactly what this change delivers and is the seam left for it. Open decision 2 in the slice spec (which backend/platform the proof uses) is not pre-empted here.

### D10: Real-backend attribution shape

At least one real agent backend executes a granted frozen Action and attributes the complete fact set to the same Run/Action: stable Session identity, host/backend/model, the real cwd (the canonical workspace the granted ActionView names), ActorRef, start/end times, structured events, usage/cost, result, stderr/diagnostics, and evidence references. The executor correlates these to the granted Action id and invocation id; the registry contributes host lifecycle facts; the canonical Record receives the completion. This realises slice acceptance 2's "at least one real supported agent backend executes an Action and associates [the complete fact set] to the same Run/Action."

## Risks / Trade-offs

- **[The matrix could drift out of sync with the shipped tiers]** -> the matrix is computed from the same declarations the hosted tiers persist at prepare time and from current-platform availability, not maintained by hand; a guard asserts the matrix matches the live declarations on every host. A prose support table was rejected for the reason in D3.
- **[execution-lost mis-typed as generic uncertainty or as workload failure]** -> the executor's reconciliation maps host `interrupted`/`turn-outcome-unknown` and launcher disappearance to the distinct `execution-lost` typed outcome, and a mutation receipt proves each classification discriminates (an `execution-lost` outcome must not be reachable for a normally-completed or normally-failed Action, and a generic uncertainty must not be labelled `execution-lost`).
- **[A crash between evidence publish and Record mutation leaves a half-set]** -> the Facade re-reads and re-verifies the complete set from the durable EvidenceStore before mutation (D5); a partial set fails the completeness check. A mutation receipt proves a half-set is rejected.
- **[Silent reroute to in-tool when hosted is unavailable]** -> the matrix returns typed `authority-unavailable` and the executor has no code path that selects `in-tool` in response; a mutation receipt proves a hosted-unavailable request fails closed rather than rerouting.
- **[Reuse policy enforced against the wrong scope boundary]** -> reuse is constrained to the same frozen invocation/role/workspace/backend-authority tuple read from the granted ActionView; a mutation receipt proves a cross-invocation or cross-authority reuse request is rejected with an auditable handoff/retire.
- **[Driver faces invent divergent control semantics]** -> all faces consume one projector/control contract; a guard proves the same RunId/ActionId is addressable from each face with no duplicated truth.
- **[The host's `turn-outcome-unknown` and the executor's `execution-lost` could be confused]** -> the host outcome vocabulary is unchanged (consumed as-is); `execution-lost` is an Action-level outcome the executor mints, layered above the host outcome, and the handoff states the mapping explicitly.
- **[Receipting execution-lost on Linux/macOS without zero-orphan could be misread as a regression]** -> the receipt shape is honest per decision 13: it proves `execution-lost` typing and uncommitted-frontier integrity, and records the orphan risk as a declared limitation, not a gate failure. Flagged for reviewer attention against the seed's obligation-1 "SUPERSEDED receipt shape" note.
- **[Extending the producer with anything signature-shaped would contradict decision 12]** -> the design introduces no key material and no signing path; a source-scan guard asserts the executor module accepts, stores, and returns no signing key or producer credential, mirroring the host's existing guard.

## Migration Plan

Additive. The executor module is new and sits between two already-frozen seams (Facade and host); it adds the capability matrix, the Action-outcome reconciliation, the transactional completion path in `complete`, the reuse/handoff/touch/retire policy, and the driver-face unification. The durable session-host registry record shape is not extended with completion truth; existing `/api/v1/sessions` and `rasen session` wire shapes stay compatible. Records created before this change carry the placeholder session block and remain readable; the executor treats a placeholder as `default`-provenance and applies its own authoritative policy on top, never silently enforcing a placeholder value as if authored. Rollback removes the executor module and restores direct Facade completion; the host and the EvidenceStore are untouched.
