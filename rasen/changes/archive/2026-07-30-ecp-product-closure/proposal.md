## Why

Every runtime capability of the 0.1.6 Executable Composite Pipelines portfolio has landed (ECP-1..4 plus the settle/association follow-ups), but the product still has **two owners of mechanical progression**: the canonical reconciler Run, and the `rasen-auto` orchestration playbook whose Step E still counts review rounds, enforces the cap, checks actor separation, and declares clean in prompt text. The research document's 0.1.6 exit conditions (`rasen/work/issue-centered-automation-platform/executable-composite-pipelines/deterministic-pipeline-kernel-research.md`, §15.4, "`0.1.6` 退出条件", lines 1828–1847) require that no entry owns independent mechanical progression, that one Run has one engine owner and one canonical state, and that every condition has evidence. This slice is the portfolio's declared **integration and deletion** closure (decomposition-plan §7): converge the entries, repair the engine-selection seams that still lie, delete the duplicated prompt-owned rules whose replacement evidence exists, and produce the evidence ledger that lets 0.1.6 exit honestly. It adds **no new runtime model**.

## What Changes

- **Engine selection becomes explicit, defaulted, and reversible.** A `runs.engine` config key (`auto | reconciler | legacy`, default `auto`) plus a `--engine` override on `rasen pipeline start`; `auto` selects the reconciler when capability discovery reports it supported and falls back to legacy otherwise; an explicit `legacy` setting makes `pipeline start` refuse with a typed error (the off-switch the research document requires). Legacy Runs keep recovering exactly as before. The bilateral engine-ownership guard (`assertSingleEngineOwner`) shipped in ecp-run-spine as a function with unit tests and **zero production callers** — dead code, discovered at task 1.7; this slice wires it into `pipeline start` and the canonical mutation seams with a declared-engine discriminator (design D8): run-state that declares `engine: reconciler` is legitimate bookkeeping beside its canonical Record, while run-state with no engine declaration (everything written before this slice) or `engine: legacy` is a legacy owner whose coexistence with a canonical Record is refused as `engine_owner_conflict` — previously that coexistence went entirely unchecked.
- **`rasen-auto` converges to selection/launch/adapter.** The orchestration playbook's Step E (prompt-owned review→fix mechanics: round counting, cap enforcement, actor-separation checking, clean determination) is replaced for reconciler-engine runs by driving the canonical Run (`pipeline start` / `resume-run` / `complete`, reading the `review-cycle` section) — the exact pattern Step L already uses for goal loops. Duplicated mechanical statements are deleted; retained mechanics are explicitly labeled as the legacy-engine path. Run-state (`auto-run.json`) is re-bounded: operational bookkeeping (workers, gate-policy freeze, retention mode, strategy attempts) stays LEAD-owned; mechanical truth (stage/round/phase/findings/outcome) derives from the canonical Record for reconciler-engine runs and can never back-drive it. This also discharges ECP-3's inherited tasks 9.3 and 9.4 (see Adjudications).
- **v1 parallel-only lowering is repaired** (Candidate 2 — IN). `resolveCapabilityBindings`/policy remapping emit v1 `stage:<id>` identities for a v1 pipeline whose only v2 construct is `parallelGroup`, while lowering routes such definitions through the v2 lowerer that looks up `root:<id>` — so `supported_v2_parallel` is production-unreachable for its intended v1 audience and a forced lowering throws. The v2-migration predicate is unified into one shared function used by binding resolution, policy remapping, and support analysis (deleting two divergent inline copies — an accidental second implementation of "what needs v2").
- **Operations consumes the review-cycle section** (Candidate 1 — IN). `getReviewCycleSection` has zero consumers in `packages/ui/src` while ECP-1's shipped delta spec (`executable-review-cycle`, "Cross-plane projection parity from one ChangeRunView") promises Operations consumption — a live false-promise. A `ReviewCycleSection` renderer is added to `OperationsSection.tsx` following ECP-4's parallel/choice pattern, with a UI parity test including deliberately-incoherent-section probes.
- **Dormant session-contract fields are declared placeholders and authored intent stops being destroyed** (design D9). Every committed agent action persists `session: { reuse, handoffTokenLimit, reuseRoundLimit }`; the two limits are hardcoded unchosen constants (`10_000` / `1`, no config key, `'default'` provenance) and the CLI resolver flattens the four authored reuse scopes to two, erasing `stage`/`run-planner`/`review-thread` distinctions. Rather than guessing new numbers (that design belongs to the 0.2.0 Session execution layer), the runtime spec now declares 0.1.6-era recorded limits non-authoritative placeholders — which retroactively protects every Record ECP-1..4 already wrote — an additive `sessionReuseAuthored` field preserves authored reuse scope verbatim (absent when unauthored; digests unchanged), and the one-shot evaluator's `sessionReuse: never` is stamped `definition` provenance because it is implied by the node's nature, not defaulted. No behavior changes; no session semantics are designed here.
- **UI parity constants get provenance by construction** (Candidate 3 — IN). The hand-copied canonical section constants move to one shared data module under `packages/ui/test/`; the node-side provenance test derives them through the real projector (the kernel's answer), and the UI parity tests import the same module — drift becomes a compile/test failure instead of a reviewer probe.
- **The two pre-existing `packages/ui` canvas test failures are closed** (Candidate 4 — IN). Both failures in `test/canvas/pipeline-canvas-page.test.tsx` (fanout/join `editor-supported` flag; missing `composite` creatable kind) are adjudicated against the shipped Canvas specs — stale expectation → fix the test with the spec cited; real product gap against "Canvas covers all first-version nodes and Composite" → fix the product. "Packaging/build/release checks pass" cannot be evidenced over a red UI suite.
- **Product wording and capability discovery are completed**: every `reconcilerSupport` reason renders as product language in CLI and the Canvas `EngineSupportPanel`; the effective engine and its source are displayed at launch and in run views; the stale architecture doc header (`docs/architecture/executable-composite-pipelines.md` still scopes 0.1.6 to root-DAG-only) is refreshed; migration/user documentation covers engine ownership, the disable switch, compatibility projections, and the upgrade path for changes holding pre-convergence run-state (`pipeline start` refuses until the legacy artifact is retired; legacy resume keeps working — the one path an existing user hits on upgrade); legacy-engine retirement conditions are **recorded, not enacted** (per the research document, retirement is decided by dogfood evidence).
- **The end-to-end dogfood matrix is completed and re-anchored on the integrated HEAD.** Existing real-Run evidence is cited (bug-fix, goal-loop-measure, goal-loop-research, full-feature, custom composite); the missing cells are produced fresh: a real `small-feature` Run, a real `goal-loop-evaluate` Run, and verification that the Custom Composite evidence is genuinely **Canvas-authored** (ECP-2's task allowed "or construct programmatically") — authoring one via Canvas if not.
- **An exit-conditions evidence ledger is produced**: all 14 conditions of research-doc §15.4 enumerated with a concrete evidence pointer each (test file, RunId, doc, or commit) — no condition is claimed without one.

**BREAKING**: none — no valid state loses a capability, but TWO fail-closed refusals are new, called out honestly: (1) a change holding BOTH pre-convergence legacy run-state and a canonical Run — a state the run-spine spec always declared invalid but nothing enforced — now refuses launch and canonical mutations with `engine_owner_conflict` instead of proceeding unchecked; (2) `rasen pipeline start` on a change holding ONLY pre-convergence legacy run-state (no canonical Run) now refuses with the same actionable error instead of creating a Run that would be born unable to advance — its very first mutation would hit refusal (1). Case (2) is what a user upgrading with old changes on disk will actually hit; the message names the legacy artifact and the two resolutions (retire the legacy run-state, or keep driving the change through legacy resume). Genuinely unchanged: legacy `pipeline resume` on those same changes, read-only `pipeline status` (unguarded by design), every canonical-only change, the `auto` engine default (reconciler where supported, legacy otherwise), and `pipeline cancel` — deliberately left unguarded so the refusal's own documented resolution (cancel the canonical Run) is always reachable.

## Adjudications (requested by the planning context)

- **Candidate 1 — IN.** Zero-consumer `getReviewCycleSection` violates ECP-1's shipped cross-plane parity requirement; "complete Operations product wording" and "cross-plane parity suite passes" both point at it, and ECP-4 left a worked pattern to copy. Leaving a shipped spec's promise silently false in the closure slice would be the worst outcome.
- **Candidate 2 — IN.** It is squarely "reconciler engine selection/default/fallback": capability discovery currently mis-reports the engine for v1 parallel-only pipelines, and the divergent v2-migration predicates are exactly the "compatibility code becoming an accidental second implementation" this slice exists to stop. The revived path is re-reviewed for semantics end-to-end, not just diffed (portfolio lesson).
- **Candidate 3 — IN.** Cheap, mechanical, and it upgrades the parity suite from "planes agree" to "planes agree with the kernel" — the shared-reader lesson made an explicit acceptance concern.
- **Candidate 4 — IN.** The release-check acceptance is unfalsifiable while the UI suite is red by baseline. Each failure gets an evidence-backed verdict (stale test vs product gap), not a blanket test edit.
- **ECP-3 tasks 9.3/9.4 — inherited, discharged here.** 9.3 is the auto convergence above. 9.4 is substantively already true in the templates (`goal-iterate.ts` and `goal-report.ts` read `sections[].kind === 'goal'`; `goal-run.json` is documented as projection-only) — this slice verifies it with grep/test evidence and annotates ECP-3's ledger with a pointer to that evidence rather than leaving the boxes silently open.
- **ECP-3 tasks 13.1–13.4 — discharged here.** They are full-suite/tsc/lint/Windows verification, which the FINAL slice must run against the integrated HEAD anyway; ECP-3 could never run them more meaningfully than this slice can. They are ticked in ECP-3's tasks.md only via an annotation citing this change's verification evidence — provenance preserved, no bare tick.

## One change or two?

One change — deliberately large but single-themed: every item either transfers mechanical ownership to the one engine, deletes a duplicate of it, or produces the evidence that the transfer is complete. The only honest split ("do the convergence" / "prove it") would ship part 1 unproven, which is precisely the false-tick failure mode this portfolio keeps paying for; the dogfood matrix and evidence ledger are the acceptance instrument of the convergence, not a separable follow-up. Size is managed by strict task ordering (engine policy → repairs → convergence → UI closure → wording/docs → dogfood → ledger → release checks), with each task externally checkable.

## Capabilities

### New Capabilities

_None. This slice deletes and converges; the engine-selection policy is an added requirement on the existing runtime capability, not a new capability._

### Modified Capabilities

- `ecp-change-run-runtime`: ADDED requirement — engine selection is explicit (`runs.engine` config + `--engine` override), defaults to the reconciler where supported, can be explicitly disabled (typed refusal), and never changes how legacy Runs recover. (Stacked delta on the unarchived `ecp-run-spine` capability, per the `ecp-settle-completeness` precedent.)
- `executable-parallel-pipelines`: ADDED requirement — a v1 pipeline whose only v2 construct is `parallelGroup` gets truthful engine-support reporting and lowers through the same v2 path as its normalized form (closing the `supported_v2_parallel` reachability hole).
- `opsx-auto-command`: MODIFIED — "Orchestrated Execution via the Pipeline Playbook" and "DAG State Resume" become engine-aware: reconciler-engine runs are driven through the canonical Run and resumed from it; auto owns selection/launch/adapter, not mechanical progression.
- `opsx-orchestration`: MODIFIED — "Gate, Loop, Parallel, and Condition Interpretation" (review-cycle loop dispatch drives the canonical Run under the reconciler engine) and "Change Directory Blackboard and Run-State" (mechanical truth lives in the canonical Record for reconciler-engine runs; `auto-run.json` is bounded to operational bookkeeping and compatibility projection).
