## Why

Six children built Store layout v2: the partitions and identities, the scope seam, the migration, the worktree pair, the four finalization outcomes, and the Store-level Issue. Each one carried its own surfaces across, and each one recorded, in writing, the surfaces it deliberately did not. This change closes that list.

It is not a tidying pass. Three of the four things it closes are places where the repository currently *disagrees with itself*, and each disagreement is invisible from the surface that owns it:

**The v1 parser is still reading v2 records.** `src/core/store/bootstrap.ts:1235` and `:2672` call `readStoreProjectRecord` — the `version: 1` membership parser — directly against a Store root, rather than `membership-layout.ts`'s layout dispatcher. Against a migrated Store's `version: 2` project catalog the parse fails, so the first **drops the project's declared knowledge bundle and emits a parse diagnostic**, and the second **reports a perfectly healthy catalog as an unreadable record**. Child 3 found both while taking its caller census, classified them `later-slice owner`, and named this change as the owner (`store-layout-v2-migration/evidence/caller-inventory.md:61`). Nothing is corrupted — neither site writes — but a migrated Store's doctor output currently accuses its own healthy data of being broken. There is no guard preventing a seventh such site; the existing census (`test/core/store-planning/planning-path-source-guard.test.ts`) bounds literal path joins and flat path helpers, and does not look at record parsers at all.

**`rasen doctor` claims to aggregate checks it does not aggregate.** Child 3 built `diagnoseLayoutMigration` — flat refs, mixed residue, an unfinished migration, orphaned partitions, a legacy record inside a v2 Store, relocated legacy Archive records — and wired it into `rasen store doctor` (`src/core/store/operations.ts:2023`). Top-level `rasen doctor` imports only `diagnoseMigrationDrift`, the older and unrelated store-migration-commands detector, under a comment that says "Surfaced here so top-level doctor aggregates the same checks `store doctor` reports" (`src/commands/doctor.ts:613-615`). That sentence is now false. A user who runs `rasen doctor` on a half-migrated Store is told it is healthy. `test/commands/doctor.test.ts` has no Store-v2 case at all.

**Nothing checks what Git did behind Rasen's back.** The accepted design is explicit that manual Git can place a Change, an Archive entry, or a canonical spec on a Store ref that no Rasen operation put there, and that doctor and CI must therefore verify committed planning facts against the current target-line record (§9.2). Children 4 and 5 both recorded that gate as a later slice's (`store-planning-worktree-bindings/design.md:237`, `store-finalization-outcomes-v2/design.md:31`). It does not exist. An Archive entry recorded for `line-0.1` sitting under `line-0.2`'s Archive partition is reported by nothing.

**An agent working in a Store v2 session is handed a write grant for two paths the Store refuses.** `src/core/change-status-policy.ts:125-130`'s `planningDirectoriesOf` joins `<root>/rasen/specs` and `<root>/rasen/changes` unconditionally, and `buildActionContext:226` feeds it `session.planning.root` — which for a `type: 'store'` planning ref is the **Store checkout root**. So the planning write grant an agent is told it may work in names exactly the two paths `layout-write-guard.ts` refuses to write, and omits `rasen/projects/<projectId>/`, which is where the session's writes actually go. This is a live Store v2 correctness bug rather than a stale read: the grant is a sandbox statement, and it is wrong in both directions at once. No sibling recorded it — it was found taking this change's census. The parallel path `buildResolvedPlanningActionContext` already receives its grant from the scope projection (`src/commands/workflow/shared.ts:93`) and is already correct, which is the evidence that the scope-derived form is the intended one and `buildActionContext` is the straggler.

**The docs still describe the layout the design replaced.** `docs/zh/file-placement-and-planning-roots.md` is the document the accepted design opens by saying it overrides — and it still carries the flat Store tree as its "Store 路径" section (lines 449-472), still says design docs are shared Store-wide (line 168), and still says `--store` and `--project` are mutually exclusive (line 476). Both copies of the Store user guide show the flat layout in their architecture diagram and their example output. The canonical `file-placement` spec was updated to v2 by children 1 and 2; the documentation was not. The specs and the docs now say different things about the same product.

Finally, the acceptance matrix the design requires (§15) has never been run as a matrix. Four Store v2 CLI journeys exist and each proves its own child. No journey carries more than one project, none carries a `win32`/`posix` path-flavor axis, and nothing anywhere compares standalone behavior before and after v2 — which is the one property the whole portfolio promised not to break.

## What Changes

- **Migrate the two remaining v1-parser read sites.** `bootstrap.ts`'s knowledge-bundle declaration reader and its `readUnreadableRecord` probe route through the layout dispatcher, so a migrated Store's project catalog is parsed as a project catalog. A healthy catalog stops being reported as unreadable, and a knowledge bundle declared in a v2 catalog stops being dropped.
- **Add the fourth census to the source guard**, in the shape children 2 and 3 established: every direct use of a single-layout parser for a layout-versioned Store record, bounded by file and by count, each classified as the dispatcher, a frozen legacy adapter, or a migration-source reader. Extended by **enumerating** entries individually — never by a directory exemption, a path prefix, or a total — because that is the difference between a gate and a formality.
- **Compose both doctors from one layout diagnosis.** `rasen doctor` reports the same planning-layout findings `rasen store doctor` reports, with the same codes and the same repairs, so the two cannot disagree. A Store whose layout cannot be diagnosed is reported as undiagnosed, not as healthy.
- **Add the target-line consistency gate the design requires.** Doctor reports an Archive entry whose recorded target line disagrees with the partition holding it, an entry whose recorded project disagrees with the partition holding it, an entry naming a target line with no catalog, and a target-line catalog whose Store ref does not resolve. Every finding names both disagreeing values and chooses neither. **Nothing is repaired**: no outcome, target line, project owner, or workspace pair is ever synthesized, and no spec delta is ever replayed — including from a non-landed Archive that was merged in by hand.
- **Make a narrowed read say it is narrowed.** A Store v2 project archive listing addresses exactly one target line; the management archive handler currently degrades an absent Archive line to an empty list, which reads to a user as "this project has no archived changes". The result states which dimension was not addressed instead.
- **Reconcile the documentation with the shipped layout**, in both languages together: the Store user guide's architecture diagram and example output, the `docs/cli.md` Store-mode `planningWriteRoots` example and archive-destination steps, and the superseded conclusions in `docs/zh/file-placement-and-planning-roots.md`, which are marked as superseded and pointed at the document that replaced them rather than quietly edited or left standing. A rule that now holds only for standalone or only for a legacy flat Store says so instead of continuing to state itself as universal.
- **Run the acceptance matrix as a matrix.** One suite walks the design's §15 axes: layout flavor (standalone / legacy flat / migrated v2) × project partition (one / several, including the same Change name in two projects) × target line (one / two concurrent) × path flavor (`win32` / `posix`). It composes the four existing journeys' fixtures rather than re-deriving them, and it adds the three axes no journey carries today.
- **Prove standalone is unchanged, by comparison rather than assertion.** A standalone lifecycle's planning locations, CLI output, and resulting files are compared against the pre-v2 behavior. No standalone or legacy-flat operation may have acquired a project selector, a target line, or a finalization outcome.

## Capabilities

### New Capabilities

- `store-v2-consistency-gates`: the repository-wide gates that keep Store v2 coherent — one shared read-only planning-layout diagnosis behind both doctors, the target-line and project-partition consistency checks over committed planning facts with their never-repair rule, the enumerated source census over layout-versioned record readers, and the standalone/legacy-flat non-regression property the acceptance matrix demonstrates.

### Modified Capabilities

- `store-planning-scope-routing`: two requirements gain one scenario each. `Machine-readable context describes scope without granting authority` gains the rule that an agent's action-context planning grant derives from the resolved scope's typed locations rather than from joining directory names onto a planning checkout root. `Every planning consumer crosses the same scope seam` gains the rule that a read consumer whose answer is narrowed by a missing scope dimension reports the narrowing instead of presenting the narrowed answer as complete. No existing scenario changes.
- `store-project-membership`: `Membership is answered by one provider that understands legacy data` gains the layout-dispatch rule and one scenario. Reading a member's record with a single-version parser becomes a defect in the reader rather than a property of the record — which is the statement the two `bootstrap.ts` sites currently contradict. No existing scenario changes.
- `docs-content-accuracy`: purely additive. One new requirement holds Store-mode documentation to the shipped layout, requires a now-conditional rule to name its case, requires translated pages to be reconciled with their source in the same change, and requires a superseded design document to be marked rather than left standing.

## Impact

- Routes `src/core/store/bootstrap.ts`'s two `readStoreProjectRecord` sites through `src/core/store/membership-layout.ts`, and extends `test/core/store-planning/planning-path-source-guard.test.ts` with the record-parser census.
- Extends `src/commands/doctor.ts` to compose the shared layout diagnosis, and factors the composition used by `src/core/store/operations.ts`'s `doctorStores` so both call one implementation. Adds the target-line consistency checks beside `src/core/store/layout-migration/diagnostics.ts`'s existing read-only findings, reading the target-line catalogs (`src/core/store/target-lines.ts`) and the Archive v2 records child 5 writes.
- Adjusts the archive read path in `src/core/management-api/archive.ts` and `task-detail.ts` to report an unaddressed target line rather than degrade to an empty listing, and the action-context grant in `src/core/change-status-policy.ts` (`planningDirectoriesOf`) to come from the resolved scope.
- Reconciles `docs/stores-beta/user-guide.md`, `docs/zh/stores-beta/user-guide.md`, `docs/cli.md`, `docs/zh/cli.md`, and `docs/zh/file-placement-and-planning-roots.md`. No locale string needed reconciliation: `src/locales/{en,ja,zh-cn}.json` carry no flat-Store planning path.
- Adds `test/commands/store-v2-acceptance-matrix.test.ts` and `test/core/store/store-v2-consistency-gates.test.ts`, extends `test/commands/doctor.test.ts` with the Store v2 cases it has none of, and adds the standalone non-regression comparison.
- **Depends on every sibling.** It reads child 3's `diagnoseLayoutMigration` and `membership-layout`, child 4's target-line catalogs, child 5's Archive v2 record — which is **unfinished at proposal time** — and child 6's aggregate query for the matrix's multi-project axis. `design.md` §9 names each consumed contract and the fallback taken if it shifts.
- **Adds no Store v2 mutator**, which the portfolio decomposition forbids for this child. Every new surface here reports; none repairs.
- **Two operations are excluded by the accepted design rather than deferred.** Children 3, 4, and 5 each wrote "a later slice's" beside them, which reads as a portfolio gap. It is not one — the design forbids each of them, so the portfolio closes with them correctly absent:
  - **Merging a planning branch into its Store integration ref.** §16 forbids it outright: 不自动 merge、rebase、force-delete branch 或 worktree. §9.1's step 6 is a step in the *human* landing protocol, and what §9.2 requires of the tool is the opposite of automation — that doctor and CI **detect and report** an inconsistent merge ("把废弃线 feature branch 直接合进新线必须被门禁报告"). That gate is delivered here, so this is complete rather than outstanding.
  - **Upgrading a relocated legacy Archive entry into an Archive v2 record.** The portfolio's locked decision is that legacy Archives "never invent Archive outcome, target-line, or workspace-pair facts that legacy evidence cannot prove" (`planning-context.md:89-90`), and §11.2's rule for migration is the same shape: no guessing, and `unresolved` blocks apply. A legacy entry generally carries none of those three facts, so an automatic upgrade would have to fabricate all three. **To get one, a user supplies the missing facts explicitly.** For the target line that route already exists — the migration mapping file accepts `defaultTargetLine` and a per-entry `targetLine` (`src/core/store/layout-migration/plan.ts:278`), which is §11.2's priority-4 audited mapping file. The **outcome** cannot come from a mapping file at all: §8.1 requires `landed` to prove its commit reachable from the target line's code ref, and requires every non-landed outcome to carry a non-empty operator reason (`superseded` additionally a `supersededBy`). No batch migration can supply either. An upgrade is therefore an **operator declaration per entry** — a finalization act belonging to `ChangeFinalizationModule`, not a compatibility sweep — which is a second, independent reason it may not land here.
  - This change reports both states rather than hiding them: a relocated legacy record is already an `info` finding from `diagnoseLayoutMigration`, and an entry whose recorded target line disagrees with the partition holding it is a new finding from the consistency gate.
