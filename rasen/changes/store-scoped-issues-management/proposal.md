## Why

The portfolio can now partition a Store by project, migrate a legacy one into that shape, prepare a bound planning/execution worktree pair, and finalize a Change into one of four outcomes. Every one of those operations addresses exactly one project. Nothing in the tree can answer a question that spans two.

That is not a missing convenience. It is the load-bearing half of the accepted design's central proposition. Layout v2 forbids a Change with more than one project owner, and it forbids a Change with none — so the moment real work spans `elftia` and `rocut`, the model has no place to put the fact that the two Changes are one piece of work. The design's answer is a Store-level Issue whose Execution Plan *references* per-project Change instances (§9.3), and the design reserves `rasen/issues/` for it (§4), lists `StoreQueryModule` as a first-class Module (§13), and specifies the aggregate API surface (§12). None of the three exists. `rasen/issues/` is an empty name in a layout diagram, `resolveStorePlanningLayoutV2Path` has no address for it, the `PlanningAddress` union child 2 shipped omits both `issue` and `execution-plan`, and no query anywhere returns content from more than one project.

The aggregate read side is missing in a way users hit today. A Store v2 aggregate space reaches `resolveProjectContentSpace`, which refuses with `project_scope_required` — correctly, because child 2's canonical rule is that Store aggregate access grants no project authority — so the management board for a migrated Store renders an error where the Store's own content should be. The refusal is right; the alternative it was supposed to have is what is absent. Without a query that is *designed* to aggregate, the pressure is to relax the refusal, and relaxing it is how a Store aggregate quietly becomes a writable flat namespace again.

Finally, the mutation side of aggregation has no guard at all. An aggregate view is a place where a project and a target line are UI filter state, and a backend that accepts a project mutation from such a view will sooner or later complete a missing scope segment from the filter the user happened to have open. The accepted design forbids that explicitly (§12: the backend SHALL NOT infer missing fields from the frontend's current filter), and there is currently no endpoint on which to state the rule.

## What Changes

- Add `rasen/issues/<issueId>/` to the layout v2 address contract as Store-level content, with `issue.yaml`, an optional narrative `README.md`, and immutable Execution Plan revisions under `plans/<revisionId>.yaml`. Issue and revision identifiers go through the same portable canonical-segment contract project and target-line ids already use, and path computation stays pure and containment-checked.
- Add an **Issue**: a Store-level record of cross-project intent with a stable `issueId`, a title, an operator-declared state (`open`, `resolved`, `dropped`), and a reason required for `dropped`. An Issue owns no Change, contains no planning content, and never appears in a project partition.
- Add an **Execution Plan**: an immutable, ordinal-numbered revision under one Issue holding a dependency graph whose nodes are either a verified `change` reference — `projectId`, `targetLineId`, `changeInstanceId` — or a declared `intent` node that names its project and target line but has no Change yet. A node is never a directory path, never a branch name, and never a `changeId` alias; the alias is recorded for humans and is explicitly not resolvable. Correcting a plan publishes a new revision; a published revision is never edited.
- **Reference, never containment, and never a back-reference.** An Issue points at Change instances; a Change is not rewritten when an Issue references it, so a Store-level write never touches a project partition on another Store ref, and a Change keeps exactly one owner. The reverse lookup — which Issues reference this Change — is derived by the query module at read time and is never persisted anywhere.
- Validate every `change` node at publication against real evidence: the referenced instance SHALL re-derive to exactly one Change in this Store, its committed identity SHALL name the node's project and target line, the project SHALL be a member of this Store, and the target line SHALL have a catalog. Zero matches is `issue_reference_unresolved`, several is `issue_reference_ambiguous`, a disagreement is `issue_reference_scope_conflict`, and another Store is refused outright. Two nodes naming one instance, and any cycle in `dependsOn`, are refused before the revision is written.
- Add `StoreQueryModule` with typed query methods — `listProjects`, `listTargetLines`, `listChanges`, `listIssues`, `showIssue`, `resolveExecutionPlan` — and no untyped path in or out. `listChanges` returns results **already grouped** by `(projectId, targetLineId)`; a flat listing is deliberately not offered, because a flat list invites the caller to regroup it from a path, which is the exact thing the accepted design's §6 exists to prevent.
- Resolve cross-project state by reading Git blobs across every target line's Store ref plus the local checkout, in the read-only per-ref shape child 3 established for inventory and child 5 established for successor resolution. Nothing is checked out, merged, or fetched.
- **A query fails closed by reporting the unknown, not by throwing.** A node that resolves nowhere is `unresolved`, one that resolves in two disagreeing places is `ambiguous`, an Issue record that differs byte-wise between two Store refs is `divergent` and no winner is chosen, and a Store ref that cannot be read is listed as an **unsearched ref** rather than silently treated as absence. Every aggregate result carries an explicit `complete` flag, so a partial answer can never be mistaken for a total one.
- Derive and report an Issue's readiness — which nodes block which — and **never write it back**. Node states inform; the operator declares the Issue's own state. An Issue is not auto-resolved by its graph.
- Add `rasen store issue new|list|show|plan|state`, `rasen store changes`, and `rasen store projects`, each with `--json` whose content matches the human form. The Issue group takes `--store` and refuses to require `--project` or `--target-line`, which is the accepted design's §7 exception made executable. Every command prints pathspec-scoped commit suggestions and stages, commits, fetches, and pushes nothing.
- Serialize Issue writes on one new owner-aware machine-root lock key, `(storeUid, issueId)`, acquired **before** any of child 4's four keys, so that child's fixed order and its no-reach-back assertion stay valid unchanged. A query takes no lock.
- Add the Store aggregate read family to the management API — `GET /api/v1/stores/:storeUid/issues`, `.../issues/:issueId`, `.../issues/:issueId/plans/:revisionId`, `.../projects`, and `.../projects/:projectId/lines/:targetLineId/changes` — computed fresh from disk on every request, and the scoped mutation `POST /api/v1/stores/:storeUid/projects/:projectId/lines/:targetLineId/changes`, which like every other management mutation writes only by spawning the CLI.
- **Make scope completeness a server-side refusal.** A project-scoped mutation reached from an aggregate surface SHALL carry Store, project, and target line in the path; the server SHALL NOT complete a missing or ambiguous segment from a query filter, a session, the launch project, or a previously viewed selection, and SHALL NOT accept a project or target line the Store's own catalogs do not declare. The Issue endpoints require the Store and explicitly do **not** require a project, so the rule is "the scope the operation needs, complete", not "always name a project".
- Render the aggregate in the UI: a Store v2 board grouped by project and target line where every card states its project, target line, Change instance, and — for an archived entry — its finalization outcome; a Store-space Issues view whose plan nodes link to the owning project's Change and show `unresolved`, `ambiguous`, and `divergent` as themselves; and an aggregate-view guard that will not submit a project mutation until the user has chosen the project and the line explicitly.
- **BREAKING (Store v2 store-space board):** on a Store space whose Store declares layout v2, the member chip row is replaced by project and target-line grouping. A card's project in layout v2 is a committed planning fact, and the chip row answers the same question from session provenance — a weaker source that can disagree. Legacy flat Store spaces keep the chip row exactly as specified. The practical impact today is small and worth stating plainly: a Store v2 aggregate space currently gets `project_scope_required` from the space-scoped changes listing, so the control being replaced is one that presently filters an error state.
- **BREAKING (management security enumeration):** the served-path set and the CLI-spawn mutation set in `management-http-api`'s security requirement grow by the Store aggregate read family and two Store-scoped mutations. Any consumer asserting the exact enumeration — including the whitelist test — sees new members. The baseline that grows is the POST-`store-finalization-outcomes-v2` one: that change already added the Store change-finalization path to both sets and `finalize-change` as the fifteenth `bounded-cli` op, so this change extends fifteen to eighteen rather than fourteen to seventeen. No existing path changes behavior.
- **Behavior tightening (not a capability loss):** an Issue write is refused from a bound planning worktree with `issue_write_requires_store_checkout`. A planning worktree's branch is one Change's unmerged line; a cross-line resource authored there is guaranteed to diverge from every other line. The repair is to run the write in a Store checkout that is not bound to a Change, which the diagnostic names.

## Capabilities

### New Capabilities

- `store-issue-resources`: the Store-level Issue and Execution Plan resource model — stable Issue identity and operator-declared state, immutable ordinal plan revisions, the two node kinds, reference-not-containment and the absence of any back-reference, publication-time reference verification against real Store evidence, graph validation, the Issue lock and its ordering relative to child 4's keys, the write-location rule, and the `rasen store issue` surface.
- `store-aggregate-query`: `StoreQueryModule`'s typed query methods, cross-ref blob reading, grouping by project and target line as a structural property of the result, node and Issue state resolution with `unresolved` / `ambiguous` / `divergent` / unsearched-ref reporting and an explicit completeness flag, derived-never-written Issue readiness, the no-spec-replay rule for aggregation, the deliberate absence of a persisted index, and the `rasen store changes` / `rasen store projects` surfaces.

### Modified Capabilities

- `store-planning-layout-v2`: purely additive. Two new requirements give Store-level Issues and Execution Plan revisions their layout v2 addresses and give Issue and revision identifiers the same portable canonical-segment contract project and target-line ids already carry. No existing requirement changes.
- `store-planning-scope-routing`: purely additive. One new requirement makes a Store-level Issue operation its own scope intent — it resolves a Store, requires no project or target line, and does not thereby gain project mutation authority — and states where such a write may land.
- `management-http-api`: the security requirement's served-path and CLI-spawn enumerations gain the Store aggregate read family and the two Store-scoped mutations; two new requirements give the aggregate read family and the scope-complete Change-creation endpoint their contracts.
- `board-ui`: the Store member chip filter is bounded to legacy flat Store spaces, and three new requirements add the Store v2 grouped board, the Store-space Issues view, and the incomplete-scope mutation guard.
- `management-ui-shell`: purely additive. One new requirement states that a Store-scoped call addresses its Store by UID through the same single client seam, and never derives that UID from the `store:<id>` space selector, which carries the Store's local id rather than its stable identity.

## Impact

- Adds `src/core/store/issues/**` (records, plan revisions, reference resolution, graph validation, publication, locks, diagnostics, adapters) and `src/core/store/query/**` (the query module, per-ref blob reading, grouping, node-state resolution), and extends `src/core/store/planning-layout-v2.ts` with the `issue` and `execution-plan` addresses and `src/core/store/planning-validation.ts` with the issue and revision identifier parsers.
- Extends `src/core/store-planning/types.ts` with a `store-issue` intent and the two typed addresses on `StoreReadAddress`, and extends `src/core/store-planning/internal/resolver.ts` to resolve that intent without a project.
- Adds `src/core/management-api/stores.ts` and its wire types beside `changes.ts` / `archive.ts` / `project-space.ts`, registers the Store route family in `src/core/management-api/router.ts` and `whitelist.ts`, and mirrors every new wire type into `packages/ui/src/api/types.ts` with `satisfies` fixtures under `test/fixtures/` — the mirror is hand-maintained and drifts silently, so it is part of the wire-type task rather than a follow-up.
- Adds `rasen store issue`, `rasen store changes`, and `rasen store projects` to `src/commands/store.ts`, `src/core/completions/command-registry.ts`, and all three locale trees (`src/locales/{en,ja,zh-cn}.json`).
- Adds the Store v2 aggregate board, the Issues view, and the mutation guard to `packages/ui/src/board/**` and `packages/ui/src/components/**`.
- Adds record, revision, graph, reference-resolution, query, grouping, scope-intent, lock, CLI, API, and UI suites, a real-CLI cross-project journey over one Store with three projects on two target lines, and Windows/POSIX address fixtures.
- Depends on `store-layout-v2-migration` for the partitions and catalogs it reads, on `store-planning-worktree-bindings` for target-line resolution and the machine workspace index that locates an unmerged planning worktree, and on `store-finalization-outcomes-v2` — now **implemented and unarchived** — for the four outcomes, the Archive v2 record, and the target-line-scoped Archive address that a node's terminal state is read from. `design.md` §11 names every consumed contract with the fallback taken if it shifts. This change adds no second route to finalization: it declares no outcome, produces no Archive record, applies no spec delta, and performs no Git write of any kind. Because it MODIFIES a `management-http-api` requirement that `store-finalization-outcomes-v2` amends, its delta is only appliable after that child has archived — the archive order for this portfolio is 3 → 4 → 5 → 6 → 7.
- Read-caller migration, the doctor and CI literal-path and layout-consistency gates, documentation reconciliation, and the full standalone/migration/worktree/finalization/management end-to-end acceptance matrix stay `store-v2-compat-hardening`'s. No Store v2 mutator is deferred into it: the Issue and Execution Plan writers and the scoped Change-creation endpoint are delivered here.
- Known remaining gap, deliberately not absorbed: a persisted aggregate index. Every query reads fresh, which is correct and is what the management API's fresh-read requirement already demands, and which is bounded by the number of target lines. A durable index would be a second source of truth about cross-ref state, and the accepted design is explicit that the machine registry is never authority; introducing one belongs to a slice that can also own its invalidation.
