### F2 — Major (pre-existing, same defect class, same edited line): `opus-4` resolves to 1M but Opus 4.0/4.1/4.5 are 200k models · **RESOLVED**

`src/core/model-presets.ts:48` — matching is case-insensitive substring,

4.1 / 4.5 id. Verified against the **same** ground truth design D14 cites for

200000  zenmux/anthropic/claude-opus-4 · 4.1 · 4.5

```
claude-opus-4-5-20251101   rasen=1000000  real=200000  WRONG

```

variants; `zenmux/openai/gpt-5` is 400,000 and `gpt-5.4`/`5.5`/`5.6` are
1,050,000. Which provider surface the preset describes is a product decision,
not a defect.

**Resolved** — `MODEL_PRESETS` now enumerates the 1M Opus generations
(`opus-4-6`, `opus-4-7`, `opus-4-8`, `opus-5`) and carries a trailing

### F3 — Major (newly introduced): `RASEN_AGENT_RUNTIME` is sticky through the whole descendant tree · **RESOLVED**

`src/core/runtimes/dispatch-adapters.ts:32,65-72`. The identity key is an
environment variable, so it is inherited transitively, and it outranks every
fingerprint (`runtime-adapters.ts:296-300`). Verified sequence:

```
1. codex host env            -> {"runtime":"codex","source":"codex-thread-id"}
2. bridged claude worker     -> {"runtime":"claude","source":"env-override"}   (the fix: correct)
3. codex grandchild of it    -> {"runtime":"claude","source":"env-override"}   <-- still carries CODEX_THREAD_ID
4. bridgeChildEnv('codex',…) -> {"runtime":"claude","source":"env-override"}   (playbook-owned arm does not clear it)
```

Pre-change, step 3 answered `{runtime:'codex',source:'codex-thread-id'}`. In
that grandchild `rasen agent context --latest` resolves through the **Claude**
session store and reports an unrelated Claude transcript's occupancy as the
Codex session's — the confident-wrong-number class D8 targets — and keepalive
gates on `runtimes.claude` instead of `runtimes.codex`.

`design.md:297` weighed only "a worker that relied on inheriting a
fingerprint", not descendants. Reachability is unproven but plausible: the
`management-api/supervisor.ts` spawn runs `claude -p` for workflow skills, and
a LEAD-shaped workflow dispatches Codex workers. Net still an improvement over
defect 3 (which mislabelled the direct worker every time), but the new hazard
is undeclared.

The clean fix needs a seam that does not exist: `codex/invocation.ts` returns
argv + stdin directive + a rendered shell string and carries no environment, so
making the key target-scoped (`RASEN_AGENT_RUNTIME: <target>` on both arms)
requires the invocation builder to surface the pair for the playbook-owned
spawn. That is a design change, hence a decision rather than a fix.

**Resolved (full fix, owner's choice)** — the identity is now TARGET-SCOPED
rather than sticky:

- `childEnv` is REQUIRED on every dispatch adapter, not just `rasen-owned`
  ones, and typed `RuntimeIdentityEnv<Id>` so the VALUE is pinned to the
  declaring runtime. `spawn` now says only WHO applies it. Both gates verified
  to fire: a claude adapter declaring codex's identity → `TS2322: Type
  'RuntimeIdentityEnv<"codex">' is not assignable to type
  'RuntimeIdentityEnv<"claude">'`; the playbook-owned adapter omitting it →
  `TS2741: Property 'childEnv' is missing`. The previous shape caught neither.
- `bridgeChildEnv` merges the target's identity **unconditionally**, so no
  ancestor's value can stand. Verified: the codex grandchild now reports
  `{"runtime":"codex","source":"env-override"}`.
- `CodexExecInvocation` gained an `env` field and `formatShellInvocation`
  renders it as a leading `RASEN_AGENT_RUNTIME='codex'` (`set "…" &&` on
  Windows), so the playbook-owned spawn Rasen cannot touch applies its own
  identity. The shipped orchestration playbook states it as a non-negotiable
  invariant beside the stdin redirect; the four affected template SHA baselines
  were recomputed.
- `RUNTIME_IDENTITY_ENV_VAR` + `runtimeIdentityEnv()` make the key/value pair a
  single leaf source that `detectHostRuntime`, both adapters and the invocation
  builder all read.

D7 amended a second time, including the correction that its original asymmetry
argument was right about the mechanism and wrong in its conclusion.
